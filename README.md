# CarClub Platform

Закрытая платформа автоклуба (iOS + Android + Web). См. `docs/TZ.md` для
полного технического задания, `docs/DECISIONS.md` для журнала
архитектурных решений, `docs/ROADMAP.md` для дорожной карты.

## Структура репозитория

```
docs/            ТЗ, решения, лицензии, дорожная карта
backend/         NestJS API (auth, invites, roles, users, module registry, chat-bridge)
web-admin/       Next.js админ-панель
mobile/          Expo (React Native) мобильный клиент
infra/           docker-compose для локальной разработки
```

## Быстрый старт (локальная разработка)

Требуется: Node.js 22+, PostgreSQL 16 (локально или через Docker).

### Backend

```bash
cd backend
cp .env.example .env   # указать DATABASE_URL, JWT_SECRET
npm install
npx prisma migrate dev
npx ts-node prisma/seed.ts   # создаёт тестового Owner + тестовый инвайт-код
npm run start:dev
```

Тестовые данные после сида (только для локальной разработки):
- Owner: `test-owner@carclub.local` / `TEST-owner-password-123`
- Инвайт-код: `TEST-INVITE-0001`

### Web-admin

```bash
cd web-admin
cp .env.example .env.local   # NEXT_PUBLIC_API_URL
npm install
npm run dev
```

### Mobile (Expo)

```bash
cd mobile
cp .env.example .env
npm install
npx expo start --dev-client
```

Обычный Expo Go не подойдёт для полной сборки — защита медиа (гл. 3.3
ТЗ, `react-native-capture-protection`) требует нативных модулей и,
соответственно, кастомного Dev Client.

#### Публикация в TestFlight / Google Play internal track (EAS)

`mobile/eas.json` содержит три профиля сборки:
- `development` — internal distribution, с `expo-dev-client`, для
  разработки;
- `preview` — internal distribution (TestFlight-эквивалент/APK для
  ручной раздачи тестерам), без dev client;
- `production` — App Store / Google Play (`app-bundle`), с
  автоинкрементом версии.

Файл **не содержит и не может содержать** реальных credentials — это
конфиг профилей сборки, а не секреты. Чтобы реально собрать и
отправить билд, нужны вещи, которые в этой сессии никто не может
создать за пользователя:

```bash
npm install -g eas-cli   # или npx eas-cli
eas login
eas build --profile preview --platform all
eas submit --profile production --platform ios     # нужен Apple Developer
                                                     # аккаунт + App Store
                                                     # Connect app record
eas submit --profile production --platform android  # нужен Google Play
                                                     # service account JSON
```

Обязательно перед первым `eas build`: активная подписка Apple Developer
Program (bundle id `club.carclub.app` уже задан в `app.json`), доступ к
Google Play Console, и `eas credentials` для привязки/генерации
подписывающих ключей — этот шаг делает владелец аккаунтов разработчика,
не описывается в репозитории.

### Через docker-compose (Postgres + backend + web-admin + Rocket.Chat + Mongo)

```bash
cd infra
docker compose up --build
```

Поднимает всё, включая Rocket.Chat (официальный образ, без лицензии
Enterprise — см. `docs/DECISIONS.md`) и однонодовый Mongo replica set,
который он требует. **Первичная настройка Rocket.Chat — вручную,
разово:**

1. Открыть `http://localhost:3100`, пройти setup wizard, создать
   первого администратора.
2. В админке RC: `Administration → Users → <admin> → Personal Access
   Tokens` — создать токен, вписать его и `userId` администратора в
   `backend/.env` как `ROCKETCHAT_ADMIN_TOKEN`/`ROCKETCHAT_ADMIN_USER_ID`.
3. Убедиться, что `CREATE_TOKENS_FOR_USERS_SECRET` в `backend/.env`
   совпадает с одноимённой переменной у сервиса `rocketchat` в
   `infra/docker-compose.yml` (нужно для `POST /chat-bridge/session`).
4. Перезапустить `backend`.

Без этой настройки `chat-bridge` работает в режиме no-op — auth и
остальной API не блокируются, но `POST /chat-bridge/session` (и,
соответственно, чат в мобильном приложении) вернёт 503.

## Тесты (backend)

Unit-тесты (моки Prisma/зависимостей, без реальной БД):

```bash
cd backend
npm test
```

E2e-тесты поднимают весь `AppModule` целиком против **отдельной**
тестовой базы (не dev-базы) — нужно один раз создать её и применить
миграции + сид:

```bash
createdb carclub_test   # или: psql -c "CREATE DATABASE carclub_test OWNER carclub;"
E2E_DATABASE_URL="postgresql://carclub:carclub@localhost:5432/carclub_test?schema=public" \
  DATABASE_URL="postgresql://carclub:carclub@localhost:5432/carclub_test?schema=public" \
  npx prisma migrate deploy
DATABASE_URL="postgresql://carclub:carclub@localhost:5432/carclub_test?schema=public" \
  npm run prisma:seed

npm run test:e2e
```

`test/setup-env.ts` принудительно переопределяет `DATABASE_URL` внутри
самого прогона тестов (на `carclub_test` по умолчанию, либо на
`E2E_DATABASE_URL`, если задан) — так что даже если в `.env` указана
dev-база, e2e-тесты её не тронут. Rocket.Chat для e2e не поднимается —
`ROCKETCHAT_*` переменные намеренно не заданы, chat-bridge работает в
уже описанном выше no-op режиме.

## Статус реализации

**Этап 1** (см. `docs/ROADMAP.md`): схема БД, backend-скелет (auth,
приглашения, заявки на вступление, роли/права, журнал аудита, реестр
модулей), веб-админка (логин, участники, приглашения, роли) — реализованы.

**Чат, этап A** (текст + группы + каналы, ТЗ гл. 3.2): реализовано —
`chat-bridge` (provisioning + выдача сессии через `users.createToken`),
`GET /users/directory`, мобильный REST/DDP-клиент Rocket.Chat
(`mobile/src/rocketchat/`, без сторонних npm-зависимостей — см.
`docs/DECISIONS.md`), экраны списка чатов/нового чата/переписки с
реалтайм-доставкой. Проверено сквозным прогоном (регистрация →
provisioning → выдача сессии → создание DM → отправка сообщения →
realtime-доставка → история) против локального мок-сервера Rocket.Chat
(протокол REST + DDP); полноценный живой Rocket.Chat не поднимался в
среде разработки этой сессии (недоступен демон Docker) — конфигурация
`infra/docker-compose.yml` не проверена вживую, только по документации
API.

**Чат, этап B** (медиа + защита, ТЗ гл. 3.3): реализовано — собственное
хранилище медиа через backend (`backend/src/media/`, байты никогда не
проходят через Rocket.Chat — только текстовый маркер-ссылка в
сообщении), AES-256-GCM шифрование at rest, токенизированная выдача
(короткоживущий JWT, привязан к получателю), динамический водяной знак
на фото (`sharp`, имя получателя + время просмотра — не хранится на
диске в раздаваемом виде), журнал доступа (`MediaAccessLog`: VIEW/
DOWNLOAD_ATTEMPT/SCREENSHOT_DETECTED), кнопка отправки фото и защищённый
просмотрщик в мобильном приложении, `react-native-capture-protection`
для защиты экрана (`FLAG_SECURE` на Android, детект скриншота на iOS).

Проверено сквозным прогоном на реальном backend: загрузка фото →
подтверждено, что байты на диске зашифрованы (не совпадают с
оригиналом) → выдача токена → получение контента → подтверждено, что
водяной знак виден (пиксельное сравнение с оригиналом) → запись в
`MediaAccessLog` → отклонение недействительного/отсутствующего токена
(401/400) и запроса к несуществующему медиа (404).

⚠️ **Не проверено на реальном устройстве:** нативная защита экрана
(`FLAG_SECURE`/детект скриншота, `react-native-capture-protection`) —
в среде разработки этой сессии нет мобильного устройства/эмулятора и
возможности собрать нативный Expo Dev Client. Код написан по
фактическим TypeScript-определениям библиотеки (`CaptureProtection.
prevent/allow/addListener`, `CaptureEventType.CAPTURED`), но живой
прогон на устройстве — необходимый шаг перед продакшеном, не
выполненный в этой сессии.

Видео: шифрование/токен/журнал доступа реализованы так же, как для
фото; водяной знак и полноценный in-app плеер — не реализованы в этом
этапе (см. `docs/DECISIONS.md` — открытый вопрос по лицензии ffmpeg для
водяного знака; плеер полученный по токенизированной ссылке открывается
в системном приложении).

**Модерация чата в web-admin** (ТЗ гл. 3.7): реализовано —
`GET /moderation/rooms` (список всех комнат через admin REST API
`rooms.adminRooms`), `GET /moderation/rooms/:id/messages` (история
через `im.history`/`groups.history`/`channels.history` с
админ-заголовками), `DELETE /moderation/rooms/:id/messages/:msgId`
(`chat.delete`) — все три за правом `chat.moderate`
(`backend/src/chat-bridge/chat-moderation.controller.ts`); бан
участника (`POST /users/:id/ban`) теперь дополнительно best-effort
деактивирует его в Rocket.Chat (`users.setActiveStatus`); новая
страница `GET /media/access-log` (тоже `chat.moderate`) — журнал
VIEW/DOWNLOAD_ATTEMPT/SCREENSHOT_DETECTED с фильтром по типу события.
Страница `web-admin/app/moderation/`.

При верификации этой функциональности обнаружен и исправлен
пред-существующий баг `PermissionsGuard`
(`backend/src/common/guards/permissions.guard.ts`): проверка читала
метаданные `@RequirePermission()` только через `context.getHandler()`,
что не видит декоратор, применённый на уровне класса контроллера — это
молча пропускало проверку прав для `ModulesRegistryController`
(`modules.manage` был де-факто не защищён от обычных авторизованных
участников). Исправлено на `reflector.getAllAndOverride(key,
[context.getHandler(), context.getClass()])`.

Проверено сквозным прогоном на реальном backend + мок-сервере
Rocket.Chat: список комнат → история сообщений → удаление сообщения →
подтверждено, что оно пропало из истории; бан участника →
подтверждён вызов `users.setActiveStatus` на мок-сервере; обычный
участник (без `chat.moderate`) получает 403 на всех эндпоинтах
модерации и на `/media/access-log`; `GET /media/access-log` проверен
на реальных данных Postgres, включая фильтр по `SCREENSHOT_DETECTED`.
Страница `web-admin/app/moderation/` проверена в браузере (Playwright
+ Chromium): вход, список комнат, открытие комнаты, удаление сообщения
по клику, журнал доступа с подсветкой `SCREENSHOT_DETECTED`.

**Refresh-токен** (найдено и закрыто при аудите на заглушки): `POST
/auth/refresh` выпускал `refreshToken` (TTL 7д), но ни один эндпоинт не
принимал его обратно, а `JwtStrategy` не проверяла поле `type` в
payload — из-за этого `refreshToken`, отправленный как обычный
`Authorization: Bearer`, проходил как полноценный access-токен (то есть
окно действия токена фактически расширялось до 7 дней вместо 15 минут).
Исправлено: `JwtStrategy.validate` отклоняет payload с `type:
'refresh'` (`backend/src/auth/jwt.strategy.ts`); добавлен `POST
/auth/refresh` (`backend/src/auth/auth.service.ts` —
`refresh()`), который проверяет тип токена, статус пользователя
(бан блокирует обновление) и выдаёт новую пару токенов. Оба клиента
(`web-admin/lib/auth-context.tsx`, `mobile/src/auth-context.tsx`)
теперь сохраняют `refreshToken` и тихо обновляют сессию по таймеру
(каждые 13 минут, до истечения 15-минутного access-токена) — раньше
`refreshToken` просто игнорировался. Проверено сквозным прогоном:
access-токен работает на защищённых роутах; тот же токен, отправленный
как refresh (и наоборот), отклоняется 401; `/auth/refresh` с
действительным refresh-токеном выдаёт новую рабочую пару; забаненный
пользователь не может обновить сессию; в реальном браузере (Playwright)
подтверждена ротация обоих токенов в `localStorage` и работоспособность
после неё.

**2FA** (найдено и закрыто при аудите на заглушки): проверка TOTP-кода
при логине уже существовала (`AuthService.login`), но поле было
опциональным для всех, обязательность 2FA для админ-ролей нигде не
проверялась, а включить её было негде — ни в web-admin, ни в mobile не
было UI, вызывающего `POST /auth/2fa/start`/`/confirm` напрямую (только
curl/Postman). Плюс мобильный логин вообще не принимал `totpCode` — при
включённой 2FA вход через приложение был бы невозможен.

Закрыто: `PermissionsGuard` (`backend/src/common/guards/permissions.guard.ts`)
теперь после проверки самого права дополнительно требует
`twoFactorEnabled: true` у аккаунта — то есть **любой** эндпоинт за
`@RequirePermission` (участники, роли, приглашения, модерация чата,
журнал аудита) отклоняется 403 с понятным сообщением, пока 2FA не
включена. Сам логин не блокируется (иначе включить 2FA было бы неоткуда
— `/auth/2fa/start` требует уже залогиненной сессии) — только
привилегированные действия. Новая страница `web-admin/app/security/`:
показывает статус 2FA, запускает `/auth/2fa/start` (секрет +
`otpauth://`-ссылка для ручного добавления в Google
Authenticator/Authy — без QR-рендеринга, чтобы не тянуть новую
зависимость под due diligence ради этого), подтверждает код через
`/auth/2fa/confirm`. Мобильный логин (`mobile/src/screens/LoginScreen.tsx`,
`mobile/src/auth-context.tsx`) теперь принимает и передаёт `totpCode`.

Заодно найден и исправлен смежный баг: `ChatBridgeService.listRooms` /
`getRoomHistory` / `deleteMessage` / `createSession`
(`backend/src/chat-bridge/chat-bridge.service.ts`) не ловили сетевые
сбои `fetch()` (Rocket.Chat недоступен) — такой сбой утекал наружу как
непойманный `TypeError` и превращался в голый `500 Internal server
error` вместо понятного ответа клиенту. Обнаружено вживую при
верификации 2FA (мок-сервер Rocket.Chat был не поднят в момент теста
страницы `/moderation`). Добавлена обёртка `rocketChatFetch()`,
переводящая сетевые сбои в `502 Bad Gateway` с понятным сообщением.

Проверено сквозным прогоном: включение 2FA (start → TOTP-код → confirm)
на реальном backend с реальной генерацией кода (`otplib`); привилегированный
эндпоинт отклоняется до включения 2FA и разрешается после; логин без
кода/с неверным кодом отклоняется, с верным — проходит; вся страница
`web-admin/app/security/` (включая ввод кода) пройдена в реальном
браузере через Playwright, включая сценарий "заблокировано → включили →
разблокировано" на странице модерации; отдельно подтверждено, что при
недоступном Rocket.Chat модерация возвращает 502 вместо 500, и что при
восстановлении связи снова работает как раньше.

**Заявки на вступление в web-admin** (найдено и закрыто при аудите на
заглушки, ТЗ гл. 2.1): backend (`GET/POST /applications`, `POST
/applications/:id/review`, `backend/src/invites/applications.service.ts`)
был полностью рабочим, но в web-admin не было ни одной страницы,
которая бы его вызывала — заявки, поданные без инвайт-кода, невозможно
было рассмотреть иначе как через curl. Добавлена страница
`web-admin/app/applications/` — список с фильтром по статусу
(на рассмотрении/одобренные/отклонённые), кнопки «Одобрить»/«Отклонить»
для заявок на рассмотрении; при одобрении backend сам выдаёт
персональный инвайт-код — страница показывает его сразу после решения.
Проверено сквозным прогоном: публичная подача заявки (без auth) →
появление в списке «на рассмотрении» → одобрение через реальный
браузер (Playwright) → выданный инвайт-код подтверждён по факту
существующим в `GET /invites`.

**Профиль и автомобили в mobile** (найдено и закрыто при аудите на
заглушки): backend (`GET/PATCH /users/me`, `POST/GET
/users/me/vehicles`) был полностью рабочим, но в мобильном приложении
не было ни одного экрана, который бы его вызывал — только чат. Добавлен
`mobile/src/screens/ProfileScreen.tsx` (доступен по кнопке «Профиль» из
списка чатов): редактирование имени, список автомобилей участника с
формой добавления (марка/модель/гос.номер — тестовые значения с
префиксом `TEST-`, см. `CLAUDE.md` — с переключателем видимости номера
другим участникам), кнопка выхода (перенесена сюда со списка чатов).
Проверено сквозным прогоном на реальном backend: `GET /users/me` →
`PATCH /users/me` с изменением имени → `GET /users/me/vehicles` (пусто)
→ `POST /users/me/vehicles` → `GET /users/me/vehicles` (машина
появилась) — все ответы совпадают по форме с тем, что ожидает экран.
⚠️ Сам экран не прогонялся визуально в эмуляторе/на устройстве (нет
эмулятора в этой среде — то же ограничение, что и для защиты экрана
выше) — только backend-контракт, код написан по актуальным сигнатурам
эндпоинтов.

## Этап 2 — игровые модули

**Фундамент геймификации** (ТЗ гл. 3.5/3.6): реестр модулей
(`ModuleDefinition`) существовал с Этапа 1, но `applyStatEvent`
(единственное место, где вообще меняется `User.pointsTotal`) никем не
вызывался, не было журнала начислений (только агрегат) и не было
web-admin страницы для управления реестром — включить модуль можно было
только через curl.

Добавлена модель `StatEvent` (журнал: кто/сколько/за что/когда,
`backend/prisma/schema.prisma`) и в
`backend/src/modules-registry/modules-registry.service.ts`:
`applyStatEventWithinTransaction(tx, event)` — атомарно (в одной
транзакции с анти-фрод-проверкой самого модуля) пишет в журнал и
инкрементит `pointsTotal`; `applyStatEvent()` — обёртка без внешней
транзакции; `assertEnabled(key)` — переиспользуемая проверка «модуль
включён»; `leaderboard(key)` — топ участников по модулю из журнала.
`ModulesRegistryController` переведён с class-level на постатейные
guard'ы (как `InvitesController`), чтобы `GET
/modules/:key/leaderboard` был доступен всем авторизованным
участникам, а не только `modules.manage`. Новая страница
`web-admin/app/modules/` — регистрация модуля, вкл/выкл, редактирование
JSON-конфига.

Заодно устранено дублирование: генератор кодов
(`ABCDE-FGHJK`-формат) был реализован **трижды** отдельно в
`invites.service.ts` и `applications.service.ts` — вынесен в общий
`backend/src/common/utils/random-code.util.ts`
(`generateRandomCode`), оба места теперь его переиспользуют.

Сид (`backend/prisma/seed.ts`) регистрирует модуль `auto-quest`
(выключенным) — чтобы на странице `/modules` сразу было что включить.

Проверено сквозным прогоном на реальном backend: `GET /modules`
(показывает сеяный `auto-quest`), включение + сохранение конфига,
`GET /modules/:key/leaderboard` доступен обычному участнику (200), но
`GET/POST/PATCH /modules` — только `modules.manage` (403 для обычного
участника); регрессия — создание инвайта и одобрение заявки всё ещё
выдают код в прежнем формате после выноса генератора в общий util.
Web-admin страница `/modules` проверена в реальном браузере
(Playwright): регистрация, вкл/выкл, редактирование конфига.

**Модуль «Авто-квест», backend** (ТЗ гл. 3.5, первый игровой модуль):
намеренно не зависит ни от LPR (заблокирован в `docs/DECISIONS.md`), ни
от реальной геолокации участников (заблокирована юридическим вопросом
по ПДн, `CLAUDE.md`) — чекпоинты верифицируются секретным кодом,
физически размещённым организаторами на месте. Реализован как обычный
NestJS-модуль внутри монолита, `backend/src/modules/auto-quest/`
(решение и обоснование — `docs/DECISIONS.md`, "Игровые модули —
физическое размещение кода"); модульность — не физическим разделением
процесса, а дисциплиной: трогает Prisma только свои таблицы
(`Quest`/`QuestCheckpoint`/`QuestCheckpointRedemption`), начисление
баллов — только через
`ModulesRegistryService.applyStatEventWithinTransaction`, доступность —
только через `assertEnabled('auto-quest')`.

Эндпоинты: `GET /quests/active` (участник, чекпоинты без кодов,
`completed` для текущего пользователя), `POST
/quests/checkpoints/:id/redeem` (участник, throttle 10/мин), `GET
/quests/:id/leaderboard` (любой авторизованный), `GET/POST/PATCH
/quests[/:id]`, `POST /quests/:id/checkpoints[/:id/regenerate-code]`
(администрирование — право `modules.manage`, уже выданное роли
`event_admin` в сиде, значит и обязательная 2FA — бесплатно через
`PermissionsGuard`). Анти-фрод: `@@unique([checkpointId, userId])` на
уровне БД (не только проверка в коде — закрывает гонку одновременных
запросов), окно активности квеста (`startsAt`/`endsAt`/`isActive`).
Best-effort публикация в чат клуба при погашении
(`ChatBridgeService.postSystemMessage`, комната — `announceRoomId` в
JSON-конфиге модуля на странице `/modules`) — не блокирует погашение,
если Rocket.Chat недоступен.

Проверено сквозным прогоном на реальном backend: `event_admin` без 2FA
получает 403 на создание квеста, с 2FA — создаёт квест и чекпоинты;
обычный участник видит чекпоинты без кодов; неверный код — 400, верный
— 201 и рост `pointsTotal`, повторное погашение — 409; **гонка**: два
одновременных запроса на один непогашенный чекпоинт (`Promise.all`) —
ровно один 201, второй 409 (подтверждает, что защита реальна на уровне
БД, а не только последовательной проверки); лидерборды квеста и модуля
совпадают с фактически погашенным; выключение модуля в реестре
блокирует и список активных квестов, и погашение (403); обычный
участник получает 403 на админ-роутах квеста. Публикация в чат — с
локальным мок-сервером Rocket.Chat: погашение при поднятом моке
реально отправляет `chat.postMessage` с ожидаемым текстом в указанную
комнату; после остановки мока погашение всё равно возвращает 201
(best-effort), ошибка — только в логах backend.

**Модуль «Авто-квест», web-admin**: `web-admin/app/quests/` — список
квестов с формой создания, страница деталей квеста
(`web-admin/app/quests/[id]/`) с добавлением чекпоинтов (код
показывается сразу после создания), кнопкой «Перегенерировать код»,
кнопкой «Завершить квест» и лидербордом. Пункт «Квесты» в

квеста через форму → открытие деталей → добавление чекпоинта с
отображением сгенерированного кода → перегенерация кода (подтверждено,
что код действительно меняется).

**Модуль «Авто-квест», mobile**: `mobile/src/screens/QuestListScreen.tsx`

пройденных/всего чекпоинтов на квест) и `QuestDetailScreen.tsx` (поле

эндпоинта "один квест" не существует, только список активных.
Проверено, что поля ответа `GET /quests/active` (`id, title,
description, points, order, completed`) совпадают 1:1 с тем, что
использует TypeScript-интерфейс экрана. ⚠️ Сам экран не прогонялся

**Модуль «Прятки», backend** (второй игровой модуль Этапа 2/3, ТЗ гл.
3.5): тот же принцип, что у авто-квеста — верификация секретным кодом
при личном контакте, не GPS и не фото-распознаванием. Механика: один
участник раунда назначается организатором «прячущимся» (hider); когда
его физически находит другой участник («seeker»), hider называет
секретный код лично, seeker вводит его в приложении и получает баллы.
`backend/src/modules/hide-and-seek/` — обычный NestJS-модуль внутри
монолита (тот же паттерн, что и `auto-quest`), новые модели
`HideAndSeekRound`/`HideAndSeekFind`, начисление баллов — только через
`ModulesRegistryService.applyStatEventWithinTransaction`, доступность —
только через `assertEnabled('hide-and-seek')`.

Эндпоинты: `GET /hide-and-seek/rounds/active` (участник, `code` не
отдаётся, `iAmHider`/`found` для текущего пользователя), `POST
/hide-and-seek/rounds/:id/find` (участник, throttle 10/мин, 400 если
`seekerUserId === hiderUserId` — нельзя погасить раунд, в котором сам
прячешься), `GET /hide-and-seek/rounds/:id/leaderboard`, `GET/POST/PATCH
/hide-and-seek/rounds[/:id]`, `POST
/hide-and-seek/rounds/:id/regenerate-code` (администрирование — право
`modules.manage`, обязательная 2FA через `PermissionsGuard`). Анти-фрод
— `@@unique([roundId, seekerUserId])` на уровне БД. Best-effort
публикация в чат при находке (`announceRoomId` в конфиге модуля,
`/modules`).

Проверено сквозным прогоном на реальном backend: `event_admin` создаёт
раунд и назначает hider'а (не owner, подтверждает работу
`modules.manage`); обычный участник видит раунды без `code`, с верными
`iAmHider`/`found`; hider не может погасить свой раунд — 400; неверный
код — 400, верный — 201 и рост `pointsTotal`; повторное погашение тем
же seeker'ом — 409; **гонка**: два одновременных запроса одного
seeker'а на один раунд (`Promise.all`) — ровно один 201, второй 409;
лидерборды раунда и модуля совпадают с фактически найденным;
выключение модуля блокирует список активных раундов и погашение (403);
обычный участник получает 403 на админ-роутах раунда; публикация в
чат — с локальным мок-сервером Rocket.Chat реально отправляет
`chat.postMessage` с ожидаемым текстом. Web-admin `/hide-and-seek`
проверена в реальном браузере (Playwright): создание раунда с выбором
hider'а из списка участников, просмотр кода, перегенерация кода
(подтверждено, что код меняется), завершение раунда.

**Модуль «Прятки», mobile**: `mobile/src/screens/HideAndSeekListScreen.tsx`
(список активных раундов, кто прячется, статус «вы прячетесь»/«найдено
✅»/баллы) и `HideAndSeekDetailScreen.tsx` (поле ввода кода и кнопка
«Нашёл!», скрыта для собственного раунда hider'а, обработка 400/409

**Псевдонимная личность в чате + самоуничтожающиеся сообщения**
(решение и обоснование — `docs/DECISIONS.md`, "Псевдонимная личность в
чате и самоуничтожающиеся сообщения"): по запросу пользователя, с
явной фиксацией архитектурного компромисса до реализации.

- Каждый участник получает `User.chatAlias` (генератор —
  `backend/src/common/utils/alias.util.ts`, свой небольшой словарь без
  внешней зависимости), который `auth.service.ts#register` передаёт в
  Rocket.Chat **вместо** `displayName`. Мобильный чат и модерация в
  web-admin читают одно и то же поле `u.name` из RC, поэтому оба
  автоматически показывают alias, а не реальное имя — в том числе
  оператору модерации. Бэкофилл для пользователей, заведённых раньше —
  `backend/prisma/scripts/backfill-chat-alias.ts`.
- Модерация не теряет функциональность: `POST /moderation/rooms/:id/messages/:msgId/ban-sender`
  (кнопка «🚫 Забанить отправителя» на странице `/moderation`)
  резолвит RC id сообщения → реальный аккаунт через
  `User.rocketChatUserId` и банит его — оператор не видит и не
  запрашивает реальное имя.
  Реальная личность по-прежнему в БД (нужна для логина/ролей/баллов/
  2FA) и по-прежнему видна там, где это осмысленно: `GET
  /users/directory` (выбор собеседника для нового чата — вы и так
  знаете реальных людей в закрытом клубе) и `MediaAccessLog` (аудит
  скриншотов/загрузок, ТЗ гл. 3.3, не может быть анонимным по своей
  природе).
- Самоуничтожающиеся сообщения — реальная функция, не декорация: TTL
  оборачивается в маркер (`mobile/src/media/ttl-marker.ts`, по образцу
  `media/marker.ts`), `POST /chat-bridge/messages/:roomId/:msgId/expire-at`
  создаёт `ExpiringMessage`, `MessageExpiryService`
  (`backend/src/chat-bridge/message-expiry.service.ts`) реальным
  `setInterval` каждые 15с находит просроченные и вызывает
  `ChatBridgeService.deleteMessage` (retry на следующем цикле, если RC
  временно недоступен — запись не теряется молча).
  `ConversationScreen` — выбор длительности (10с/1м/1ч/24ч), круговой
  countdown, локальное скрытие содержимого по истечении.
- Явно не реализовано (см. `docs/DECISIONS.md`): звонки (нет
  WebRTC-инфраструктуры — не добавляю неработающую вкладку по правилу
  «без заглушек»); настоящее end-to-end шифрование (не заявляется,
  пока не построено, — правило `CLAUDE.md` про честные обещания).
- Проверено сквозным прогоном на реальном backend: `chatAlias` у новых
  пользователей уникален, в `users.create`/`users.update` к
  Rocket.Chat уходит alias, не `displayName`; `GET
  /moderation/rooms/:id/messages` отдаёт alias; бан по сообщению
  реально банит нужного пользователя (проверено по записи в
  `AuditLog`); сообщение с TTL=10с реально удаляется через мок RC
  `chat.delete` по истечении срока, сообщение без TTL не трогается;
  `GET /users/directory` по-прежнему отдаёт реальные имена.

**Не реализовано** (следующие итерации): push-уведомления;
автоматическое уведомление администратора при детекте скриншота
(событие пишется в журнал, отдельного канала уведомлений нет); лента
жалоб/репортов от пользователей (RC `moderation.reportsList` не
встроена в наш UX); временный мут участника (только полный бан);
реакции/reply/forward/поиск по сообщениям/статус прочтения;
self-destruct-сообщения; реальный деплой в облако; модуль LPR
(заблокирован до решения по бюджету — `docs/DECISIONS.md`); общий
лидерборд/лента клуба по всем модулям сразу (Этап 3).
