# Квест Платформа — техническая спецификация

Платформа для проведения городских квестов на трёх площадках: **веб**, **Android**, **iOS**.
Один бэкенд, один контракт, одна бизнес-логика.

---

## 1. Продукт

| Роль | Что делает |
|---|---|
| Игрок | Регистрируется, видит таймер и задания, сдаёт коды (вводом или QR). Баллов и мест не видит |
| Судья | Называет команде код оценки качества на точке |
| Организатор | Управляет игрой, редактирует задания, видит табло, игроков и журнал попыток |

Экраны: регистрация → игра → (админка отдельно, только веб).

## 2. Архитектура

```
apps/
  api/       @workspace/api-server   Express 5 + SQLite        :8080
  web/       @workspace/quest        Vite + React 19           :21234
  mobile/    @workspace/quest-mobile Expo (iOS + Android)
lib/
  core/      @workspace/core         Zod-схемы, таймер, гео, офлайн-очередь
  db/        @workspace/db           SQLite: схема, миграции, мапперы
  api-client/@workspace/api-client   Транспорт + хуки TanStack Query
  api-spec/  @workspace/api-spec     Генератор openapi.yaml
```

`lib/core` и `lib/api-client` используются вебом и мобилкой **без изменений**.
Различается только слой представления: DOM в вебе, React Native в мобилке.

### Источник правды — Zod

Схемы в `lib/core/src/schemas.ts` дают:
- runtime-валидацию тел запросов на сервере,
- типы для обоих клиентов,
- `lib/api-spec/openapi.yaml` (генерируется через `pnpm run gen:openapi`).

> Отступление от исходного ТЗ: там источником правды была рукописная `openapi.yaml`,
> а клиент генерировался из неё Orval'ом. Рукописная спека расходится с кодом,
> который на самом деле валидирует запросы, и расхождение всплывает во время игры.
> Здесь спека — производная от кода, а не наоборот. `openapi.yaml` по-прежнему
> существует и пригоден для внешних потребителей.

## 3. Три инварианта

### 3.1 Время считает сервер

Таймер выводится из полей события и **времени сервера**:

```
elapsed   = reference − startedAt − totalPausedMs
reference = pausedAt, если на паузе; иначе now
remaining = clamp(durationMs − elapsed, 0, durationMs)
```

Каждый ответ содержит `serverTime`. Клиент один раз вычисляет поправку часов
(`clockSkew`) и дальше тикает локально раз в секунду. Перевод системных часов
на телефоне не добавляет и не отнимает игрового времени; устройства в разных
часовых поясах показывают один и тот же остаток.

Пауза не расходует игровое время: её длительность уходит в `totalPausedMs`.

### 3.2 Идентификация — токен, не clientId

`POST /api/register` возвращает токен **один раз**. В БД лежит только SHA-256.
Токен хранится в SecureStore (мобилка) и localStorage (веб).

Повторная регистрация с тем же `deviceId` возвращает **того же игрока** с новым
токеном: переустановка приложения не теряет прогресс команды.

> Исходное ТЗ хранило `clientId` в localStorage и идентифицировало игрока им.
> Это позволяет подставить чужой идентификатор и играть за чужую команду.

### 3.3 Отправки идемпотентны

Клиент генерирует `idempotencyKey` (UUID) **в момент постановки в очередь**.
Ограничение `UNIQUE (team_id, idempotency_key)` гарантирует однократный зачёт
даже при многократной доставке из офлайн-очереди.

Отдельный частичный индекс `UNIQUE (team_id, task_id) WHERE status = 'accepted'`
закрывает гонку двух устройств одной команды на уровне БД.

## 3.4 Конец игры и видимость итогов

Игра **не останавливается**, когда кто-то закрыл все задания. Команды, дошедшие
до финиша, ждут остальных. Игра кончается ровно двумя способами:

| Способ | Что происходит |
|---|---|
| Таймер дошёл до нуля | статус → `finished` автоматически |
| Организатор нажал «Стоп» | статус → `finished` |

Автозавершение обеспечивают два механизма: ленивая проверка при каждом чтении
события и фоновый обход раз в 5 секунд (`startAutoFinish`). Второй нужен потому,
что время кончается само по себе — без него истёкшая игра осталась бы в статусе
`running` с открытой регистрацией, пока кто-нибудь не дёрнет API.

При завершении часы замирают: момент остановки пишется в `paused_at`, и
`computeClock` перестаёт считать. Иначе завершённая игра через час показывала бы
совсем другой «остаток».

### Итоги видит только организатор

Счёт и места — сведения для организатора. Игрок не видит их **никогда**:
ни во время игры, ни после её окончания. Итоги объявляет организатор.

Реализовано не скрытием в интерфейсе, а отсутствием данных в API — поля,
которого нет в ответе, невозможно подсмотреть в обход экрана:

| Что | Игрок | Организатор |
|---|---|---|
| Сумма баллов команды | нет в ответе `/api/tasks` | `/api/admin/events/{slug}/scoreboard` |
| Баллы за сданный код | нет в `SubmitCodeResponse` | там же |
| Табло и места | публичного маршрута нет | там же + CSV |
| Номинал **сданного** задания | `null` | полный список с кодами |
| Номинал **несданного** задания | виден | виден |

Номинал сданного задания скрыт не из перестраховки: если у сданных заданий
видно «+15», игрок складывает их и восстанавливает свой счёт. У несданных
номинал остаётся — он нужен для выбора маршрута и о счёте команды не говорит.

Отметка «сдано» видна всегда: без неё игрок не поймёт, что ему осталось.

По завершении игры вместо списка заданий игрок видит нейтральный экран:
сколько заданий закрыл и «итоги объявит организатор». Ни баллов, ни места,
ни чужих команд.

### Сохранность итогов

`submissions` и `quality_claims` не удаляются ни при завершении, ни по времени.
Единственное, что стирает результаты — команда `reset`, и она защищена дважды:

1. **Подтверждение названием.** `reset` требует поля `confirmation` с точным
   названием события. Одного нажатия кнопки недостаточно.
2. **Снимок в архив.** Перед удалением итоги пишутся в `event_archives`.
   Снимок пишется и при обычном завершении игры.

Архив хранит JSON табло и переживает удаление самого события, поэтому итоги
проведённого квеста нельзя потерять в принципе.

## 4. Приём кода: порядок проверок

1. **Повтор по ключу идемпотентности** → вернуть исходный результат
2. Игра идёт? → `game_not_running`
3. Лимит попыток (12 отказов за минуту на команду) → `rate_limited`
4. Задание уже закрыто командой? → `already_solved`
5. Гео-проверка (если у задания заданы `lat/lng/radiusM`) → `too_far`
6. Сравнение кода после нормализации → `wrong_code` или **зачёт**

Нормализация кода: trim, верхний регистр, удаление пробелов, `E`/`Ё` → `Е`.
Ввод «` quest-7 `» засчитывается против кода `QUEST-7`.

Гео-проверка прибавляет к радиусу погрешность GPS, но не больше **75 м**:
в застройке accuracy честно доходит до 50 м, а без ограничения достаточно
сообщить `accuracyM: 10000` и сдавать коды из дома.

## 5. Офлайн

Городской квест идёт во дворах и подвалах. Отправка при отсутствии сети:

1. `ApiError.status === 0` (сеть) или `>= 500` → попытка уходит в `OfflineQueue`
2. Очередь лежит в AsyncStorage / localStorage и переживает перезапуск
3. Раз в 15 секунд фоновый flush отправляет накопленное **в порядке добавления**
4. Игрок видит счётчик «N кодов отправятся автоматически»
5. После 8 неудач попытка отбрасывается, чтобы очередь не росла бесконечно

Отказ сервера по существу («не тот код») очередью **не** обрабатывается —
попытка доставлена, результат показывается сразу.

## 6. Обновления в реальном времени

SSE: `GET /api/events/{slug}/stream` отдаёт `{"type":"game-state"|"tasks-changed"}`.
Событие — сигнал перезапросить данные, а не сами данные: так не возникает
расхождения между потоком и запросом.

- **Веб** — `EventSource` (сам переподключается)
- **Мобилка** — опрос раз в 15 с; EventSource в RN нет, а polyfill ради одного
  потока не окупается и хуже переживает засыпание приложения
- **Фолбэк** — TanStack Query дополнительно опрашивает раз в 30 с

## 7. Схема БД

```
events         id, name, slug, status, duration_ms, started_at, paused_at, total_paused_ms
teams          id, event_id, name                          UNIQUE (event_id, name)
players        id, event_id, team_id, name, role, token_hash, device_id, last_seen_at
tasks          id, event_id, order_index, title, description, code, points,
               verification, lat, lng, radius_m, quality_enabled
submissions    id, event_id, task_id, team_id, player_id, idempotency_key,
               status, points_awarded, lat, lng
quality_codes  id, event_id, code, points, label
quality_claims id, event_id, team_id, task_id, quality_code_id, player_id, idempotency_key
attempt_log    id, event_id, team_id, player_id, task_id, value, ok, reason
event_archives id, event_id, event_name, event_slug, reason, finished_at,
               duration_ms, team_count, results_json
```

Всё привязано к `event_id`: платформа проводит несколько квестов, а не один
глобальный. Миграции — по списку в `lib/db/src/schema.ts`, применяются один раз
и записываются в `schema_migrations`.

Настройки SQLite: `WAL` (табло админа не блокирует приём кодов),
`busy_timeout = 5000` (одновременная запись ждёт вместо `SQLITE_BUSY`),
`foreign_keys = ON`.

Табло считается запросом, а не накопительным счётчиком: счётчик рано или поздно
разъезжается с фактами после `reset` или отмены зачёта.

## 8. Анти-чит

| Приём | Механизм |
|---|---|
| Перебор кодов | 12 отказов в минуту на команду → `rate_limited` |
| Ответ виден в devtools | `GET /api/tasks` не содержит поля `code` |
| Сдача не с точки | гео-проверка с ограниченной поблажкой на accuracy |
| Передача кодов между командами | `attempt_log` — журнал всех попыток с временем и командой |
| Подстановка чужого игрока | токен вместо clientId, в БД только хеш |
| Накрутка времени | таймер серверный |
| Игра «на табло», а не по заданиям | счёта и мест нет в игровом API вовсе |
| Потеря итогов от промаха по «Сброс» | подтверждение названием + снимок в архив |

## 9. Права

- **Игрок** — `Authorization: Bearer <token>`
- **Организатор** — `X-Admin-Token`, общий секрет из `ADMIN_TOKEN`

Сервер **не стартует** без `ADMIN_TOKEN`: админка без секрета означает, что
управление игрой доступно любому. Сравнение токена — постоянного времени.

## 10. Что осталось за рамками

Реализовано не всё из предложенного; ниже — честный список пропусков.

| Не сделано | Почему / что нужно |
|---|---|
| Режим гонки | Игра всегда идёт до таймера или «Стоп». Автостоп по первому финишу или по заполнению топ-3 не реализован |
| Экран итогов в архиве по CSV | Архив показывается в админке, отдельной выгрузки снимка нет |
| Фото-задания | Нужно хранилище файлов и экран модерации; `verification: 'photo'` в схеме есть, обработчика нет |
| Push-уведомления | Требуется Expo push-токен, таблица подписок и триггеры на старте/финише |
| Роли judge/organizer | Поле `role` в БД есть, отдельного интерфейса судьи нет |
| Админка в мобилке | Управление игрой только в вебе |
| Мультисобытийный UI | API многособытийный, клиенты работают с одним `eventSlug` из конфигурации |
| Postgres | SQLite достаточно до нескольких сотен устройств на один процесс |
