# CarClub Platform — инструкции для Claude Code

Закрытая платформа автоклуба: iOS + Android + Web. Чат (аналог Telegram) с
защитой медиа, модульная система игр/квестов, распознавание номеров по
фото с начислением баллов, админ-панель с ролями. Полное ТЗ — `docs/TZ.md`.

## Обязательно прочитать перед началом работы

1. `docs/TZ.md` — полное техническое задание (главы 1–8 + Приложение A)
2. `docs/DECISIONS.md` — какие архитектурные развилки уже решены, какие ещё нет
3. `docs/LICENSING.md` — **разрешённые и запрещённые зависимости**. Проверять
   перед добавлением любой новой библиотеки, не полагаться на память.
4. `docs/ROADMAP.md` — порядок разработки по этапам

## Критические правила — не нарушать

1. **Не добавлять зависимость, не проверив её лицензию по `docs/LICENSING.md`.**
   Если библиотеки там нет — искать её LICENSE-файл на GitHub и добавлять
   запись в `docs/LICENSING.md` перед использованием, а не после.
   GPL/AGPL/сильный copyleft — по умолчанию запрещены без явного одобрения
   человека (см. причину в `docs/LICENSING.md`).
2. **Защита медиа — не обещать невозможного.** Полный запрет скриншотов на
   iOS и Web технически недостижим (см. ТЗ, глава 3.3). Реализовывать
   многоуровневую защиту (водяной знак + журнал доступа + детект на iOS),
   не пытаться найти несуществующий API полной блокировки.
3. **Не собирать ПДн раньше времени.** Гос.номера, фото с привязкой к
   людям, геолокация — не начинать сбор реальных (не тестовых) данных, пока
   в `docs/DECISIONS.md` юридический вопрос не помечен как закрытый.
4. **Модульность — не опция, а требование архитектуры.** Игровые модули
   (квест, прятки и т.д.) должны подключаться/отключаться через реестр
   модулей на backend, не быть жёстко вшиты в ядро (см. ТЗ, глава 3.5).
5. **LPR/геймификация — не начинать реализацию, пока в `docs/DECISIONS.md`
   не закрыт вопрос бюджета** (покупка лицензии / стороннее API / своя
   модель — см. ТЗ, глава 3.4). Это архитектурная развилка, не деталь.
6. **Двигаться по `docs/ROADMAP.md` поэтапно.** Не пытаться поднимать
   iOS+Android+Web+все модули одновременно с нуля. Текущий этап — см.
   `docs/ROADMAP.md`, раздел "Текущий этап".

## Технологический стек

См. `docs/DECISIONS.md` — там зафиксировано, что уже решено, а что ещё
нет. Не выбирать стек самостоятельно там, где в `DECISIONS.md` стоит
статус "не решено" — сначала спросить пользователя.

## Как работать с этим репозиторием

- Каждое архитектурно значимое решение (не мелкий рефакторинг, а выбор
  библиотеки/фреймворка/подхода к защите данных) — сначала фиксировать в
  `docs/DECISIONS.md` с датой и обоснованием, потом реализовывать.
- При обнаружении расхождения между ТЗ и тем, что технически осуществимо —
  не молча отклоняться от ТЗ. Явно сообщать пользователю и предлагать
  обновить `docs/TZ.md`.
- Тестовые/учебные данные (фейковые гос.номера, тестовые аккаунты) —
  помечать очевидно как тестовые (например, префикс TEST-), чтобы не
  спутать с реальными ПДн при случайном коммите.

## Структура репозитория (заполняется по мере разработки)

```
docs/            — ТЗ, решения, лицензии, дорожная карта (этот набор файлов)
backend/         — появится на Этапе 1
web-admin/       — появится на Этапе 1
mobile/          — появится на Этапе 2 (после решения по стеку)
modules/         — игровые модули, появятся на Этапе 2-3
```
