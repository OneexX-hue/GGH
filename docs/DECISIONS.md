## Мобильный стек (iOS + Android)

**Статус:** решено 08.08.2026
**Решение:** React Native (Expo + Dev Client — обычный Expo Go не
поддерживает нативные модули защиты медиа, поэтому нужен кастомный dev
client со сборкой).
**Обоснование:** рекомендация ТЗ гл. 5.1 — один код на iOS+Android,
экономия на разработке/поддержке при масштабе 5000+ участников; для
защиты медиа (гл. 3.3) уже проверена совместимая MIT-библиотека
`react-native-capture-protection` (резерв — `react-native-screenguard`,
тоже MIT) — см. `LICENSING.md`.
**Следствие:** можно начинать каркас мобильного клиента (`mobile/`).
Полный чат-функционал в приложении — после стабилизации `chat-bridge` в
backend (интеграция с Rocket.Chat).

## Хостинг

**Статус:** решено 08.08.2026
**Решение:** облако (AWS/Yandex Cloud — выбор конкретного провайдера
отдельным пунктом, не блокирует архитектуру).
**Обоснование:** рекомендация ТЗ гл. 6 — auto-scaling снижает риск
падения сервиса в пиковые моменты мероприятий (массовые фото/видео от
участников одновременно).
**Следствие:** архитектура (модульность, отдельные схемы БД,
S3-совместимое хранилище медиа) по-прежнему не завязывается на
провайдер-специфичные сервисы (например, AWS Lambda) без отдельного
решения — выбор провайдера ещё предстоит.

## Чат-бэкенд

**Статус:** решено 08.08.2026, формулировка по сборке уточнена 09.08.2026
**Решение:** Rocket.Chat, официальный образ/сборка **как есть**, без
покупки лицензии Enterprise.
**⚠️ Уточнение 09.08.2026 (важно, отменяет часть исходной записи):**
исходная формулировка «сборка из исходников с исключением
`ee/`-директории» оказалась технически неверна и не была проверена по
факту. Официального способа исключить `ee/` из сборки не существует —
мейнтейнер Rocket.Chat подтвердил на форуме отсутствие такого пути
(«Currently we don't have a guide for this»), простое удаление папки
ломает сборку на хардкодных импортах на `ee/`. По факту: код `ee/`
**физически присутствует** в любой стандартной сборке/образе Rocket.Chat,
но его функциональность **не активна без лицензионного ключа
Enterprise** — ключ в проект не вводится и не покупается. Это не «код
отсутствует», а «код есть, но выключен» — более мягкая, но честная
гарантия, принятая пользователем осознанно для закрытого self-hosted
использования внутри клуба (не редистрибуция вовне).
**Обоснование:** готовое чат-ядро экономит время разработки
относительно чат-бэкенда с нуля; лицензия чище, чем у Matrix/Synapse
(AGPLv3 с 2023 — потребовала бы либо коммерческую лицензию Element,
либо менее зрелый форк conduwuit); UX ближе к консьюмерскому
мессенджеру, чем у Zulip (заточен под тематические треды команд).
**Следствие:** наш backend (NestJS) остаётся источником истины по
пользователям/ролям/инвайтам; Rocket.Chat используется как чат-движок
под капотом через REST/Realtime API и webhooks (слой `chat-bridge`),
не форкается и не редактируется напрямую — это упрощает обновления
апстрима. Используется официальный Docker-образ `rocket.chat`
(Docker Hub) — не кастомная сборка из исходников.

## LPR (распознавание номеров) — бюджетный путь

**Статус:** ⚠️ не решено — блокирует начало разработки модуля 3.4
**На столе (см. `LICENSING.md` для деталей лицензий):**
1. Купить лицензию (Ultralytics Enterprise или Numplate RIAder API)
2. Стороннее платное API распознавания номеров (без встраивания кода)
3. Своя модель на permissive-компонентах (например, YOLOX-based, требует
   ML-экспертизы и времени на дообучение под РФ-номера)
**Действие для Claude Code:** НЕ реализовывать модуль LPR (гл. 3.4), пока
этот пункт не переведён в «решено». Остальную разработку это не блокирует.

## Геймификация/баллы — движок

**Статус:** решено (рекомендация)
**Решение:** не использовать Oasis (`isuru89/oasis`) как прод-зависимость
— лицензия подходит (Apache-2.0), но проект незрелый (75 звёзд, «всё ещё
в разработке», один мейнтейнер). Использовать его архитектуру
(events → rules engine → rewards) как референс для собственного, более
лёгкого движка на основном стеке backend.
**Обоснование:** см. ТЗ гл. 3.6 и Приложение A.

## Защита медиа — библиотека для React Native

**Статус:** решено (условно — при выборе React Native как мобильного стека)
**Решение:** `react-native-capture-protection` (MIT, активно
поддерживается) как основной вариант; `react-native-screenguard` (MIT)
как резервный.
**Обоснование:** оба проверены построчно (LICENSE-файл, активность
релизов) — см. Приложение A в `docs/TZ.md`.
**Зависит от:** решения по мобильному стеку (см. выше). Если выбор падёт
на Flutter или нативную разработку — нужны отдельные эквиваленты
(`screen_protector` для Flutter, `FLAG_SECURE`/`ScreenCaptureKit`-детект
нативно) — не проверялись в этой сессии, требуют отдельного due diligence.

## Rocket.Chat клиентская интеграция (мобильный REST/DDP-клиент)

**Статус:** решено 09.08.2026
**Решение:** не использовать `@rocket.chat/sdk` с npm. Мобильный клиент
(`mobile/src/rocketchat/`) — собственный тонкий REST-клиент (fetch) +
минимальный DDP-клиент поверх нативного `WebSocket`, без новых
npm-зависимостей.
**Обоснование (due diligence перед добавлением зависимости, см.
`CLAUDE.md`):**
- Опубликованная на npm версия `@rocket.chat/sdk` (`0.2.9-2`) не
  обновлялась с 2019 года, зависит от Node-only `node-rest-client`
  (не совместим с окружением React Native без доработок), и есть
  открытый непочиненный issue именно про несовместимость с RN
  (`RocketChat/Rocket.Chat.js.SDK#77`).
- Даже официальное мобильное приложение Rocket.Chat не использует
  npm-пакет — оно зависит от отдельной git-ветки `#mobile` того же
  репозитория, которая никогда не публиковалась в registry. Тянуть
  стороннюю непубликуемую git-ветку в зависимости противоречит духу
  правил лицензирования/сопровождения проекта (см. `LICENSING.md`).
- Использованные эндпоинты Rocket.Chat REST API (`users.createToken`,
  `im.create`, `groups.create`, `channels.create`, `chat.postMessage`,
  `subscriptions.get`, `*.history`) и базовый DDP-хендшейк
  (`connect`/`login` с resume-токеном/`sub stream-room-messages`)
  задокументированы и достаточно просты, чтобы написать тонкую обвязку
  самостоятельно — без риска брошенной зависимости.
**Следствие:** новых записей в `docs/LICENSING.md` для мобильного
чат-клиента не требуется — код собственный, сторонних лицензий нет.
