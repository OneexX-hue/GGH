## Хостинг

**Статус:** решено 08.08.2026, конкретный провайдер выбран 14.08.2026
**Решение:** облако, провайдер — **Timeweb Cloud** (выбор
пользователя/владельца клуба).
**Обоснование:** рекомендация ТЗ гл. 6 — auto-scaling снижает риск
падения сервиса в пиковые моменты мероприятий (массовые фото/видео от
участников одновременно). Timeweb Cloud — российский облачный
провайдер с дата-центрами в РФ, что упрощает соответствие требованию
152-ФЗ ст. 18 ч. 5 (локализация хранения ПДн граждан РФ на серверах в
РФ) — см. «Юридическая проработка ПДн» ниже.
**Следствие для архитектуры:** архитектура по-прежнему не завязывается
на провайдер-специфичные управляемые сервисы (Lambda-аналоги и т.п.) —
не нужны, т.к. backend/web-admin/Rocket.Chat/coturn разворачиваются как
обычные Docker-контейнеры на VPS/Kubernetes, а `S3StorageAdapter`
(`backend/src/media/storage/s3-storage.adapter.ts`) уже провайдер-
агностичен (работает с любым S3-совместимым API через `S3_ENDPOINT`) —
кода менять не требуется, только заполнить `.env` на проде:
`MEDIA_STORAGE_DRIVER=s3`, `S3_ENDPOINT`/`S3_REGION`/`S3_BUCKET`/
`S3_ACCESS_KEY`/`S3_SECRET_KEY` — точные значения endpoint/региона/имени
бакета взять из личного кабинета Timeweb Cloud → Object Storage на
момент реального деплоя (не фиксируем здесь конкретный хост, чтобы не
разойтись с интерфейсом провайдера).
**Открыто:** конкретный тип инстанса/кластера (отдельный VPS на
контейнер vs managed Kubernetes) — не архитектурный вопрос, решается
на этапе реального деплоя без изменений кода.

## Чат-бэкенд

**Статус:** решено 08.08.2026, формулировка по сборке уточнена 09.08.2026
**Решение:** Rocket.Chat, официальный образ/сборка **как есть**, без
покупки лицензии Enterprise.
**⚠️ Уточнение 09.08.2026 (важно, отменяет часть исходной записи):**
исходная формулировка «сборка из исходников с исключением
`ee/`-директории» оказалась технически неверна и не была проверена по
факту. Официального способа исключить `ee/` из сборки не существует —
мейнтейнер Rocket.Chat подтвердил на форуме отсутствие такого пути
(«Currently we don't have a guide for this»), простое удаление папки
ломает сборку на хардкодных импортах на `ee/`. По факту: код `ee/`
**физически присутствует** в любой стандартной сборке/образе Rocket.Chat,
но его функциональность **не активна без лицензионного ключа
Enterprise** — ключ в проект не вводится и не покупается. Это не «код
отсутствует», а «код есть, но выключен» — более мягкая, но честная
гарантия, принятая пользователем осознанно для закрытого self-hosted
использования внутри клуба (не редистрибуция вовне).
**Обоснование:** готовое чат-ядро экономит время разработки
относительно чат-бэкенда с нуля; лицензия чище, чем у Matrix/Synapse
(AGPLv3 с 2023 — потребовала бы либо коммерческую лицензию Element,
либо менее зрелый форк conduwuit); UX ближе к консьюмерскому
мессенджеру, чем у Zulip (заточен под тематические треды команд).
**Следствие:** наш backend (NestJS) остаётся источником истины по
пользователям/ролям/инвайтам; Rocket.Chat используется как чат-движок
под капотом через REST/Realtime API и webhooks (слой `chat-bridge`),
не форкается и не редактируется напрямую — это упрощает обновления
апстрима. Используется официальный Docker-образ `rocket.chat`
(Docker Hub) — не кастомная сборка из исходников.

## LPR (распознавание номеров) — бюджетный путь

**Статус:** решено 12.08.2026
**Решение:** вариант 2 из трёх предложенных — стороннее платное API
распознавания номеров, без встраивания чужого кода/модели в проект.
**Обоснование:** не требует ML-экспертизы и времени на дообучение (в
отличие от варианта 3, своя модель), не требует покупки Enterprise-
лицензии с неопределёнными условиями (вариант 1) — интеграция сводится
к одному REST-вызову за фото, стоимость линейно масштабируется с
реальным использованием.
**Адаптер:** `backend/src/modules/lpr/adapters/lpr-adapter.interface.ts`
(`LprAdapter.recognize(imageBuffer): Promise<LprResult>`), по тому же
паттерну, что `StorageAdapter` (`backend/src/media/storage/`) —
позволяет сменить вендора без переписывания модуля. Рабочая реализация
— `PlateRecognizerAdapter` (api.platerecognizer.com/v1/plate-reader/,
Snapshot API, публичная документация, есть бесплатная пробная квота).
**Важная оговорка:** конкретный аккаунт/API-ключ у вендора должен
завести пользователь — Claude Code не может зарегистрировать
сторонний платный сервис от чужого имени. Без `LPR_API_KEY` в `.env`
модуль возвращает понятную ошибку конфигурации при попытке
распознавания, не падает молча и не притворяется рабочим.

## Игровые модули — физическое размещение кода (Этап 2)

**Статус:** решено 11.08.2026
**Решение:** первый игровой модуль (авто-квест) реализован как обычный
NestJS-модуль **внутри монолита backend** (`backend/src/modules/auto-quest/`,
подключается в `AppModule.imports`), а не как физически отдельный
пакет/сервис.
**Обоснование:** `module-integration.interface.ts` (интерфейс
`GameModuleIntegration`) описывает модуль как отдельный пакет вне ядра —
это модель на будущее (Этап 4, физическое масштабирование), но текущий
монолит не умеет грузить внешние пакеты как плагины, и городить это
ради одного модуля преждевременно. Модульность на этом этапе
обеспечивается не физическим разделением процесса, а дисциплиной кода:
модуль трогает Prisma только свои таблицы (`Quest*`), начисление баллов
идёт только через `ModulesRegistryService.applyStatEventWithinTransaction`
(не пишет `User.pointsTotal` напрямую), доступность — только через
`ModulesRegistryService.assertEnabled('auto-quest')`. Выключение модуля
в реестре реально блокирует все его эндпоинты — то есть поведенческая
модульность (ТЗ гл. 3.5) соблюдена, просто без отдельного процесса/БД.
**Следствие:** интерфейс `GameModuleIntegration` остаётся
документацией на будущее — реализовывать его как класс сейчас не даёт
выгоды в монолите. Физическое разделение (отдельная БД/сервис, ТЗ гл.
5.4) — Этап 4, ничего в текущем дизайне этому не мешает позже.

## Хранилище медиа в чате

**Статус:** решено 09.08.2026
**Решение:** собственное хранилище через backend (не встроенная
загрузка файлов Rocket.Chat). Rocket.Chat используется только как
транспорт текстового маркера-ссылки на медиа (например
`##CARCLUB_MEDIA##{"mediaId":"..."}` в теле сообщения) — сами байты
никогда не проходят через RC.
**Обоснование:** это единственный способ реально выполнить главу 3.3
ТЗ (шифрование at rest, токенизированная выдача, водяной знак, журнал
доступа). Если бы файлы хранились/раздавались средствами RC, у нас не
было бы контроля над этими требованиями — глава 3.3 стала бы
невыполнимой по архитектуре, а не по технической сложности.
**Следствие:** backend получает новый модуль `media` (см. код) с
интерфейсом `StorageAdapter` — dev-реализация на локальной ФС,
S3-совместимый адаптер для прода — отдельная задача, зависящая от
нерешённого выбора облачного провайдера (см. «Хостинг» выше).

## Веб-чат участника (ТЗ 5.2) — CORS-требование к Rocket.Chat

**Статус:** решено 12.08.2026
**Решение:** веб-версия чата участника (`web-admin/app/chat`)
переиспользует тот же паттерн, что и мобильный клиент — тонкий REST-
клиент к Rocket.Chat API (`web-admin/lib/rocketchat/rest-client.ts`,
скопирован 1:1 с `mobile/src/rocketchat/rest-client.ts`) и ту же
сессию, выданную существующим `POST /chat-bridge/session` (никакого
отдельного веб-аккаунта в RC не заводится). Обновление сообщений —
поллингом раз в 4 секунды, не полноценный DDP/WebSocket realtime —
достаточно для веб как второстепенного клиента, mobile остаётся
основным реал-тайм каналом. Отправка защищённых фото/видео из веб-чата
не реализована — это возможность только мобильного клиента (та же
логика шифрования/маркеров, что и раньше).
**Обнаруженное при реализации ограничение, ранее не задокументированное:**
браузерный `fetch` из `web-admin` — это **другой origin**, чем сам
Rocket.Chat, и подчиняется CORS, в отличие от `fetch` в React Native
(мобильный клиент никогда не был подвержен этому ограничению, поэтому
вопрос не всплывал раньше). **Для прод-инстанса Rocket.Chat
обязательно нужно явно включить CORS** для origin веб-админки:
Administration → General → REST API → секция "CORS", добавить домен
`web-admin` в список разрешённых origin'ов (или включить `Enable CORS`
с явным списком, не `*` — небезопасно для инстанса с реальными
пользовательскими данными). Без этой настройки веб-чат в проде получит
ошибку сети в браузере при первом же запросе к RC REST API, при этом
backend и мобильный клиент продолжат работать нормально — стоит
проверить эту настройку отдельно при разворачивании прод-инстанса RC,
это легко упустить, так как локальная разработка (мок-сервер) её не
требует.

## Водяной знак на фото — библиотека

**Статус:** решено 09.08.2026
**Решение:** `sharp` (npm) для наложения текстового водяного знака на
фото на backend.
**Обоснование (due diligence по первоисточникам):** ядро `sharp` —
Apache-2.0. Прекомпилированные бинарники libvips, которые `sharp`
подтягивает как `optionalDependencies`, — **LGPL-3.0-or-later**,
подключаются динамической линковкой (стандартная практика для этой
экосистемы, официально совместима с проприетарным/закрытым кодом —
именно для этого LGPL и существует, в отличие от GPL/AGPL). Активно
поддерживается (релиз 0.35.3, июль 2026).
**Почему не GPL/AGPL-блокировка по правилу проекта:** правило
`CLAUDE.md`/`LICENSING.md` требует обязательного одобрения человека для
GPL/AGPL/«сильного copyleft». LGPL при динамической линковке — «слабый»
copyleft, не накладывающий обязательств на код приложения, и не
подпадает под это ограничение. Решение принято как архитектурное, без
блокирующего вопроса пользователю, с явной фиксацией здесь для
прозрачности.
**Резерв, если потребуется полностью уйти от LGPL-зависимостей:**
`jimp` — чистый JS, MIT, без нативных бинарников, но медленнее и с
менее качественным рендерингом текста.

## Водяной знак на видео — решено: клиентский оверлей, не ffmpeg (13.08.2026)

**Статус:** решено — водяной знак на видео реализован без
перекодирования байтов, ffmpeg не подключается вообще, вопрос его
лицензии больше не блокирует эту часть медиа.

**Исходная проблема (оставлена для истории):** наложение водяного
знака на видео на сервере (тем же способом, что и на фото — `sharp`
поверх декодированных байтов) потребовало бы перекодирования
(ffmpeg или аналог). Лицензия ffmpeg зависит от того, какие кодеки/
фильтры включены в конкретную сборку — базовая сборка обычно LGPL, но
многие практически нужные кодеки (например, некоторые h264-энкодеры)
тянут GPL-компоненты — по правилу 1 CLAUDE.md такие компоненты
запрещены без явного одобрения человека.

**Принятое решение:** водяной знак рисуется как UI-слой поверх
встроенного видео-плеера (`mobile/src/media/ProtectedMediaViewer.tsx`,
компонент `ProtectedVideoPlayer` на `expo-video`) — тот же текст, что
и на фото (имя зрителя + ISO-время, `viewerDisplayName` теперь
возвращается вместе с токеном из `MediaService.issueAccessToken`),
но композируется на клиенте, а не встраивается в байты видео.
Технически это стало возможно только сейчас — до этого у видео вообще
не было встроенного защищённого плеера (`Linking.openURL` в системный
плеер), поэтому UI-оверлей было не на чем показывать.

**Явное ограничение (правило 2 CLAUDE.md — не обещать невозможного):**
это UI-слой, а не встроенный в файл знак. Он виден при записи экрана
(вместе с остальным UI) и при обычном воспроизведении, но не защищает
сам файл видео, если он получен в обход плеера (например, через прямой
перехват сетевого трафика к токенизированной ссылке — тот же класс
риска, что уже описан для фото в ТЗ гл. 3.3). Уровень защиты
сопоставим с тем, что уже есть у фото (сервер тоже не может помешать
эксфильтрации байт «в принципе», см. правило 2), но для видео это
UI-слой, а не встроенный в изображение пиксель.

## Rocket.Chat клиентская интеграция (мобильный REST/DDP-клиент)

**Статус:** решено 09.08.2026
**Решение:** не использовать `@rocket.chat/sdk` с npm. Мобильный клиент
(`mobile/src/rocketchat/`) — собственный тонкий REST-клиент (fetch) +
минимальный DDP-клиент поверх нативного `WebSocket`, без новых
npm-зависимостей.
**Обоснование (due diligence перед добавлением зависимости, см.
`CLAUDE.md`):**
- Опубликованная на npm версия `@rocket.chat/sdk` (`0.2.9-2`) не
  обновлялась с 2019 года, зависит от Node-only `node-rest-client`
  (не совместим с окружением React Native без доработок), и есть
  открытый непочиненный issue именно про несовместимость с RN
  (`RocketChat/Rocket.Chat.js.SDK#77`).
- Даже официальное мобильное приложение Rocket.Chat не использует
  npm-пакет — оно зависит от отдельной git-ветки `#mobile` того же
  репозитория, которая никогда не публиковалась в registry. Тянуть
  стороннюю непубликуемую git-ветку в зависимости противоречит духу
  правил лицензирования/сопровождения проекта (см. `LICENSING.md`).
- Использованные эндпоинты Rocket.Chat REST API (`users.createToken`,
  `im.create`, `groups.create`, `channels.create`, `chat.postMessage`,
  `subscriptions.get`, `*.history`) и базовый DDP-хендшейк
  (`connect`/`login` с resume-токеном/`sub stream-room-messages`)
  задокументированы и достаточно просты, чтобы написать тонкую обвязку
  самостоятельно — без риска брошенной зависимости.
**Следствие:** новых записей в `docs/LICENSING.md` для мобильного
чат-клиента не требуется — код собственный, сторонних лицензий нет.

## Псевдонимная личность в чате и самоуничтожающиеся сообщения (Этап 2/3)

**Статус:** решено 11.08.2026
**Решение:** по запросу пользователя (референс дизайна — тёмный
чёрно-белый мессенджер с масками/анонимностью/таймером
самоуничтожения) вводится **псевдонимная личность на уровне
отображения в чате**: у каждого участника — персональный alias
(`User.chatAlias`), который Rocket.Chat показывает как имя профиля
вместо реального `displayName`. И мобильное приложение, и
web-admin-модерация читают одно и то же поле `u.name` из Rocket.Chat,
поэтому оба автоматически показывают alias, а не настоящее имя —
**в том числе оператору модерации**, который читает историю сообщений.
Модерация по-прежнему возможна: новый эндпоинт «забанить отправителя
этого сообщения» резолвит `msg.u._id` (RC id) → реальный аккаунт через
уже существующую связь `User.rocketChatUserId` и вызывает обычный
`UsersService.ban()`, не показывая оператору реальное имя.
Самоуничтожающиеся сообщения — реальная функция (TTL на сообщение,
серверный sweep реально удаляет через `chat.delete`), не заглушка.

**Что осознанно НЕ меняется** (иначе ломается остальная платформа):
- `MediaAccessLog` (журнал доступа к защищённым фото/видео — ТЗ гл.
  3.3, детект скриншотов/скачиваний) — остаётся с реальной личностью.
  Это требование комплаенса/безопасности, а не чат, и оно прямо
  противоречило бы своей цели, если бы стало анонимным.
- `GET /users/directory` и выбор собеседника для нового чата —
  остаётся с реальным `displayName`. Участник закрытого клуба выбирает
  собеседника из тех, кого и так знает в реальной жизни; показывать
  ему alias вместо имени человека, которого он сам выбрал, не даёт
  никакой анонимности, только путаницу.
- Роли, права, начисление баллов (квесты/прятки), бан — всё по-прежнему
  привязано к реальному `userId`. Технически «анонимность даже для
  админов» в буквальном смысле (когда сообщение вообще нельзя связать
  с аккаунтом) несовместима с банами/ролями/баллами — тогда некого
  банить и некому начислять. Реализованная модель — единственная,
  которая совместима с остальной архитектурой: реальная личность
  остаётся в БД (обязательна для логина/2FA/ролей), не показывается в
  UI чата.

**Явно исключено из объёма** (по тем же принципам, что и ffmpeg/LPR
выше — не реализовывать, пока не решено, и явно сообщать, а не тихо
недоделывать):
- **Звонки** — в референсе есть вкладка/иконки звонка, но в проекте
  нет WebRTC/сигнальной инфраструктуры. По правилу этой сессии («не
  оставляй заглушки — все функции кнопки логика должна быть») кнопка
  звонков не добавляется вообще, а не добавляется неработающей.
- **Настоящее end-to-end шифрование** — в референсе есть фраза
  «Шифрование: сообщения и звонки защищены сквозным шифрованием». По
  `CLAUDE.md` правилу 2 («не обещать невозможного») эта фраза никуда
  не идёт, пока реального E2E нет. В UI — честная формулировка про
  транспортное шифрование (HTTPS/WSS), без слова «сквозное».

**Обоснование:** зафиксировано перед реализацией, т.к. это
архитектурно значимое решение (правило `CLAUDE.md`) — меняет то, как
модерация видит отправителей сообщений по всей платформе.

- **Исчезающие сообщения** — показывается как информационная строка

- **Шифрование** — показывается как некликабельная информационная
  строка (не `<button>`, в ките это тоже декоративный `<button>` без
  действия) с честной формулировкой: шифрование данных at rest
  (AES-256) + защищённый транспорт (HTTPS/WSS) — без слова «сквозное»,
  см. уже принятое решение выше по E2E.
- **Файлы и медиа** (счётчик) — реализуется по-настоящему, но с
  честной оговоркой: считаем реальные медиа-маркеры в уже загруженной
  истории комнаты (не полный архив за всё время — full-text поиск по

- **Закреплённые сообщения, «Очистить историю», «Удалить чат»** — в

  участника (только модератор может удалить отдельное сообщение) —
  эти три пункта кита **не переносятся** в этом проходе, а не
  добавляются неработающими. Задача на будущее — см. `docs/ROADMAP.md`.

**Обоснование:** визуальный редизайн сам по себе не архитектурное
решение, но перенос конкретных элементов интерфейса кита один-в-один

## WebRTC-звонки — архитектура (сигнализация, клиенты, STUN/TURN)

**Статус:** решено 12.08.2026

### Сигнализация

Свой WebSocket-шлюз в NestJS: `@nestjs/websockets` + `@nestjs/platform-ws`
(оба MIT, проверено по `package.json` на npm registry — та же
экосистема, что и уже используемые `@nestjs/*` пакеты) поверх пакета
`ws` (MIT). Не socket.io — он тянет за собой отдельный клиентский SDK
(`socket.io-client`) на web и mobile ради возможностей (комнаты,
автопереподключение via long-polling fallback), которые здесь не
нужны: сигнализация — это всего пара сообщений на звонок (offer/
answer/ICE-кандидаты), обычный `WebSocket` (нативный и в браузере, и в
React Native) справляется без дополнительного клиентского пакета —
ровно тот же принцип, что уже применён к отказу от `@rocket.chat/sdk`
(см. «Rocket.Chat клиентская интеграция» выше — не тащить SDK ради
малой части функциональности).

**Backend ничего не знает о содержимом звонка** — только пересылает
сигнальные сообщения (`offer`/`answer`/`ice-candidate`/`call-user`/
`end-call`) от одного авторизованного пользователя другому по
WebSocket-соединению; сам медиапоток (аудио/видео) идёт напрямую
между клиентами (или через TURN, если прямое соединение невозможно),
backend его никогда не видит и не может видеть — это фундаментальное
свойство WebRTC, не наша реализация.

**Аутентификация WS-соединения** — JWT access-токен в query-параметре
URL (`wss://.../calls?token=...`), не в заголовке: браузерный
`WebSocket` API не поддерживает произвольные заголовки при рукопожатии
(ограничение спецификации, не наша реализация), поэтому query-параметр
— единственный кросс-платформенный вариант без дополнительных
библиотек. Токен проверяется в `handleConnection`, невалидный —
соединение закрывается сразу.

**Идентификация — по реальному `userId`, не по псевдониму.** Это
осознанно отличается от чата: звонок и так требует заранее знать, кому
звонишь (участник выбирает собеседника из `GET /users/directory`, где
показываются реальные имена — то же самое решение, что уже
зафиксировано выше для выбора собеседника в чате). Скрывать личность
собеседника от самого звонящего невозможно и бессмысленно — он сам её
выбрал.

### Presence и релей

`CallsGateway` держит в памяти `Map<userId, WebSocket>` подключённых
пользователей (кто сейчас онлайн для звонков на ЭТОМ инстансе). `call-user`
от A к B: если B подключён к этому же инстансу — переслать сигнал напрямую;
если нет — сначала проверить через Valkey pub/sub, не подключён ли B к
**другому** инстансу (см. «Масштабирование на несколько инстансов» ниже);
если офлайн вообще везде — сразу ответить A `user-offline` (честно, не
оставлять звонящего в неведении).

### Масштабирование на несколько инстансов (Valkey pub/sub) — решено 13.08.2026

**Статус:** решено — presence эволюционировал с «in-memory, один процесс»
(явное ограничение MVP из первой версии этой записи) на multi-instance-safe
через Valkey pub/sub, по явному запросу пользователя.

**Почему не Redis:** с версии 8.0 Redis — три-лицензия RSALv2/SSPLv1/AGPLv3
(проверено `WebFetch` реального `redis/redis/LICENSE.txt`), все варианты
либо proprietary source-available, либо сильный copyleft — запрещены по
умолчанию правилом 1 CLAUDE.md без явного одобрения. Вместо этого —
**Valkey**, форк Redis под Linux Foundation, BSD-3-Clause (проверено
`valkey-io/valkey/COPYING`), протокол идентичен — тот же клиент `ioredis`
(MIT) работает без изменений. См. `docs/LICENSING.md` за полным сравнением.

**Дизайн:** локальная `Map<userId, WebSocket>` остаётся источником истины
для самого WS-соединения (сокет физически не передать между процессами).
Два механизма поверх Valkey:
1. **Presence-набор** `calls:online` (Valkey `SET`) — `SADD` при
   подключении, `SREM` при отключении. Нужен, чтобы `call-user` мог
   синхронно ответить `user-offline`, если получателя вообще нет ни на
   одном инстансе (без этого пришлось бы либо ждать таймаут, либо
   ошибочно считать офлайном тех, кто просто на другом инстансе).
2. **Pub/sub-канал** `calls:relay` — сигнальное сообщение, которое
   локальная `Map` не может доставить (получатель не на этом инстансе,
   но есть в `calls:online`), публикуется в канал; **все** инстансы
   подписаны и, получив сообщение, проверяют свою локальную `Map` —
   доставляет тот инстанс, у которого получатель реально подключён.

**infra/docker-compose.yml:** сервис `valkey` (`valkey/valkey:8-alpine`).

**Не проверено вживую в этой сессии:** реальный многоинстансовый прогон
через `docker compose up --scale backend=2` недоступен (нет Docker-демона
в песочнице) — та же честная оговорка, что и у остального
`infra/docker-compose.yml`. Проверено иначе, но по-настоящему: все 13
существующих unit-тестов `CallsGateway` проходят без изменения поведения
(single-instance путь не тронут) + 3 новых unit-теста multi-instance-пути
(мок presence) + отдельный ручной прогон против **реального** `redis-server`
(бинарник из apt, протокол идентичен Valkey — тот же `ioredis`-клиент)
поднятого локально в песочнице: два независимых объектных графа
`CallsGateway`+`CallsPresenceService` (эмулируют два backend-процесса —
каждый со своей локальной `Map<userId, socket>`), оба подключены к одному
реальному Redis-протокол-серверу по TCP. Пользователь A подключён только к
"инстансу 1", пользователь B — только к "инстансу 2"; вызов `call-user` от
A к B прошёл через настоящий `SISMEMBER`/`PUBLISH`/`SUBSCRIBE` (не моки) и
реально доставился в сокет B на "инстансе 2" — подтверждает, что сама
pub/sub-логика релея корректна против настоящего Redis-протокол-сервера,
не только против jest-моков. Не хватает только полноценного
docker-compose с реальным `valkey` контейнером и двумя *отдельными
процессами* backend (не двумя объектами в одном процессе) — это и есть
недостающая часть проверки, ограниченная отсутствием Docker-демона.

### Клиенты

- **web-admin** — нативный browser API (`RTCPeerConnection`,
  `navigator.mediaDevices.getUserMedia`) — без новых npm-зависимостей.
- **mobile** — `react-native-webrtc` (MIT, проверено по `package.json`
  на npm registry, активно поддерживается — релизы 124.x). Требует
  Expo config plugin (сборка через `expo-dev-client`, как и
  `react-native-capture-protection` — обычный Expo Go всё равно не
  подходит для этого приложения, см. README) и разрешений камеры/
  микрофона.

### STUN/TURN

Self-hosted `coturn` (BSD-3-Clause, проверено по `LICENSE` в
официальном репозитории `coturn/coturn`) в `infra/docker-compose.yml`
— тот же принцип, что уже применён к Rocket.Chat: не завязываемся на
конкретного облачного провайдера (см. «Хостинг» — провайдер ещё не
выбран), STUN/TURN поднимается как обычный Docker-сервис. Для
локальной разработки без поднятого `coturn` клиенты используют
публичный Google STUN (`stun:stun.l.google.com:19302`) как дефолт —
достаточно для прямого P2P-соединения между клиентами в одной сети;
TURN нужен только для реальных NAT-ограничений на проде.
**Prod-предупреждение:** `coturn` в docker-compose настроен со
статическим shared secret для локальной разработки — для прода нужны
time-limited REST-credentials (`coturn` это поддерживает через
`use-auth-secret`), это отдельный шаг конфигурации при реальном
развёртывании, не код.

### Явно в объёме этого прохода (MVP)

Аудио/видеозвонок 1-на-1 между двумя онлайн-участниками: набор номера
(выбор собеседника из уже открытого чата — кнопки в шапке диалога),
входящий вызов (баннер принять/отклонить), экран активного звонка
(локальное/удалённое видео, mute, завершение).

### Явно вне объёма (по тому же принципу, что и раньше — не молчать, а явно сообщать)

- **Групповые звонки** — реализованы отдельным проходом ниже (mesh, до
  4 участников) — были вне объёма MVP, но добавлены по запросу
  пользователя.
- **Push-уведомление о входящем звонке при закрытом приложении** —
  сигнализация работает только пока WS-соединение живо (приложение
  открыто/в фоне недолго). Полноценный CallKit (iOS)/ConnectionService
  (Android) интеграция с VoIP push — отдельная большая задача.
- **История звонков** (кто кому звонил, длительность) — реализована
  отдельным проходом выше («История звонков» — блок G).
- **Запись звонков** — не реализуется (см. честную формулировку про
  отсутствие E2E-заявлений — запись потребовала бы отдельного
  правового основания, см. «Юридическая проработка ПДн» ниже).
- **Масштабирование сигнализации на несколько backend-инстансов** —
  реализовано отдельным проходом выше (Valkey pub/sub).

**Обоснование:** архитектурно значимое решение (новый транспорт —
WebSocket, новая нативная зависимость на mobile, новый сетевой сервис
в infra) — зафиксировано до кода по правилу `CLAUDE.md`.

## Групповые звонки — mesh, до 4 участников (решено: упрощённый mesh-вариант)

Пользователь явно выбрал упрощённый mesh-вариант (не SFU/медиасервер)
через `AskUserQuestion` при планировании этого прохода. Реализовано
поверх существующего `CallsGateway` (см. «WebRTC-звонки — архитектура»
выше), без нового сетевого сервиса.

**Протокол** (`backend/src/calls/calls.gateway.ts`): новые события
`join-call-room`/`leave-call-room` от клиента, `room-peers`/
`peer-joined`/`peer-left`/`call-room-full` от сервера. Сервер держит
только список участников комнаты — `Map<callRoomId, Set<userId>>` (и
обратный индекс `Map<userId, Set<callRoomId>>` для очистки при
disconnect) — сам медиапоток по-прежнему не обрабатывает и не видит
(тот же принцип, что и у 1:1-сигнализации). Существующие события
`offer`/`answer`/`ice-candidate` переиспользованы без изменений: поле
`callId` в mesh-режиме содержит `callRoomId`, а `to`/`from` указывают
на конкретного участника сетки — маршрутизация на клиенте различает
1:1-звонок и групповую комнату по тому, есть ли активный `callRoomId`,
совпадающий с `callId` входящего сообщения.

**Кто кому шлёт offer:** только что присоединившийся участник получает
от сервера список уже присутствующих (`room-peers`) и сам инициирует
`offer` к каждому из них; уже находящиеся в комнате участники получают
`peer-joined` (информационно, ждут входящий `offer`) и отвечают
`answer` при получении `offer`. Это даёт полный граф соединений (mesh)
без необходимости серверу участвовать в согласовании.

**Лимит участников — 4** (`MAX_CALL_ROOM_SIZE` в `calls.gateway.ts`):
mesh — это `N*(N-1)/2` прямых P2P-соединений на N участников; при 4
участниках это уже 6 соединений на клиента (каждый шлёт свой видеопоток
трижды) — разумный практический потолок без выделенного SFU/медиасервера.
Больше 4 участников потребовало бы отдельного медиасервера
(mediasoup/Janus и т.п.) — сознательно не делается в этом проходе,
явно вне объёма.

**Комната звонка = комната чата:** для группового/канального чата
`callRoomId` — это тот же `roomId` Rocket.Chat-комнаты, отдельного
понятия "id комнаты звонка" не вводится ни на клиенте, ни на сервере.
Кнопки группового звонка в шапке чата (web-admin `app/chat/page.tsx`,
mobile `ConversationScreen.tsx`) показываются только для не-DM комнат
(`roomType !== 'd'`) — для DM по-прежнему используется 1:1-флоу
(`startCall`/`call-user`).

**Клиент** (`web-admin/lib/calls/calls-context.tsx`,
`mobile/src/calls/calls-context.tsx`): отдельное состояние `group`
(параллельно 1:1-состоянию `CallState`, не unified-тип — пользователь
физически не может быть в 1:1-звонке и в групповой комнате
одновременно, но в коде проще держать раздельно) — `Map<peerUserId,
RTCPeerConnection>` в `groupPcsRef`, стримы участников — массив
`{userId, stream}` в React-состоянии для перерисовки сетки. `CallOverlay`
на обеих платформах рендерит сетку плиток (`call-grid`/`GroupTile`)
вместо единственного удалённого видео — своя плитка + по одной на
каждого участника, лейбл с именем (резолвится тем же
`resolvePeerName`, что и в 1:1-режиме).

**Явно вне объёма этого прохода:**
- **История звонков для групповых** — `Call`-модель (блок G) пишет
  только 1:1-звонки (`callerId`/`calleeId`), групповые звонки в неё не
  попадают — потребовало бы модели с произвольным числом участников,
  отдельная задача.
- **Push о групповом звонке** — как и для 1:1, push о входящем звонке
  не реализован (см. ограничение выше), для группового режима это
  тем более не актуально: участник presence-проверяется, только если
  уже открыл чат.
- **Более 4 участников / SFU** — см. обоснование лимита выше.

**Верификация:** `npx jest src/calls` — 22/22 (16 существующих + 6
новых на join/leave/room-peers/peer-joined/peer-left/call-room-full/
disconnect-cleanup), `tsc --noEmit` чисто на backend/web-admin/mobile.
Живой сквозной прогон — Playwright, 3 независимых браузерных контекста
(`TEST-webrtc-x/y/x2@carclub.local`, реальный backend + Postgres +
мок Rocket.Chat, fake-media-devices Chromium), все трое присоединяются
к общей групповой комнате «Тест-группа» и запускают групповой
видеозвонок: у каждого участника в сетке ровно 3 плитки (своя + два
собеседника) с реальными видеоэлементами и корректно резолвленными
именами; после выхода одного участника у оставшихся двоих сетка
корректно сжимается до 2 плиток. Подтверждает полный mesh (каждый
видит каждого), а не только пару звонящий/принявший, как в 1:1-тесте.

## Юридическая проработка ПДн

**Статус:** ⚠️ в процессе (14.08.2026) — ещё не закрыт, сбор реальных
данных участников по-прежнему не начинать
**Решение по роли:** юридическую проверку берёт на себя владелец клуба
лично (не привлекается сторонний юрист) — `docs/legal/privacy-policy-draft.md`
явно допускает эту роль («[ЗАПОЛНЯЕТ ЮРИСТ/ВЛАДЕЛЕЦ КЛУБА]»).
**Прогресс 14.08.2026:** черновик политики конфиденциальности заполнен
текстом по разделам 6 (права участника), 7 (возрастные ограничения),
8 (изменения политики) — стандартные формулировки под 152-ФЗ, готовы к
проверке владельцем. Раздел 1 («кто обрабатывает данные») частично
заполнен реквизитами владельца — ИП, зарегистрирован в РФ (уточнено:
«Мексика» из первого ответа — текущее местонахождение владельца, не
юр.адрес ИП), ИНН и контактный email получены. **Не закрыто:** полное
ФИО ИП (получены только инициалы), ОГРНИП, реальный юридический адрес
регистрации ИП в РФ — ещё не предоставлены. **Требует внимания:**
предоставленный ИНН (`080808080808`) — 12 цифр, но повторяющийся
паттерн, нетипичный для реально присвоенного номера — владелец должен
явно подтвердить его, сверив с реальным свидетельством, до публикации
(см. пометку в самом черновике).
**Закрывается пунктом:** этот статус переходит в «решено» только после
явного одобрения владельцем клуба итогового текста
`docs/legal/privacy-policy-draft.md` целиком (включая раздел 1) — до
этого момента реальные ПДн реальных участников не собирать, только
тестовые/демо-данные (см. `CLAUDE.md`, правило 3).
