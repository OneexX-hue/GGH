## Этап 1 — MVP (можно начинать сейчас, частично)

Цель: аутентификация по приглашениям + базовый чат (текст/фото/видео) +
защита медиа + профиль + минимальная админ-панель.

### Можно начинать без ожидания решений по DECISIONS.md:

1. **Схема БД** — пользователи, роли (расширяемая таблица ролей, не
   хардкод — см. ТЗ гл. 2), приглашения/инвайт-коды, объекты клуба
   (профиль/авто)
2. **Backend-скелет** — REST/GraphQL API для auth, приглашений, профилей;
   структура под будущий модульный реестр (гл. 3.5), даже если модулей
   ещё нет
3. **Система приглашений** — одноразовые/многоразовые/персональные
   инвайт-коды, заявки на вступление с модерацией (гл. 2.1)
4. **Аутентификация** — телефон/email, refresh-токены, 2FA обязательна
   для админ-ролей (принудительно на уровне привилегированных действий,
   не на уровне логина) — готово
5. **Admin-панель (базовый каркас)** — список участников, управление
   приглашениями, управление ролями

### Разблокировано решениями в DECISIONS.md, в разработке:

6. **Чат-ядро** — решено (Rocket.Chat, официальный образ, без лицензии
   Enterprise — см. `DECISIONS.md`). Реал-тайм текст/группы/каналы
   (мобильный REST/DDP-клиент, `chat-bridge` в backend) — готово. Фото/
   видео + защита медиа (см. п.7) — готово (фото; видео — без
   водяного знака, см. п.7). Модерация в web-admin (список
   комнат/сообщений, удаление сообщений, бан с деактивацией в RC,
   журнал доступа к медиа с фильтром по `SCREENSHOT_DETECTED`) —
   готово.
7. **Защита медиа (гл. 3.3)** — готово: собственное хранилище
   медиа через backend, шифрование at rest, токенизированная выдача,
   водяной знак на фото (`sharp`, встроен в байты сервером), журнал
   доступа, `react-native-capture-protection` на мобильном клиенте.
   Видео — встроенный защищённый плеер (`expo-video`, не системный
   плеер) с водяным знаком-оверлеем (имя зрителя + время, UI-слой
   поверх плеера, не встроен в байты — ffmpeg не подключался, см.
   `DECISIONS.md`, "Водяной знак на видео — решено: клиентский
   оверлей"). S3-совместимый `StorageAdapter` (`@aws-sdk/client-s3`, любой
   S3-провайдер через `endpoint`) готов — включается
   `MEDIA_STORAGE_DRIVER=s3` в `.env`, по умолчанию всё ещё локальная ФС.
8. **Деплой/инфраструктура** — зависит от хостинга (решено: облако, но
   конкретный провайдер не выбран) — локальная разработка через
   `infra/docker-compose.yml` не блокируется.

## Этап 2 — Модули и LPR

- Модульная система: реестр модулей, единый интерфейс интеграции (гл. 3.5) — готово
- Система баллов/статистики (референс — архитектура Oasis, своя реализация) —
  журнал событий + лидерборд по модулю готовы, web-admin `/modules` готов
- Первый игровой модуль (авто-квест) — готово (backend + web-admin +
  mobile; без LPR/геолокации — верификация чекпоинта по секретному
  коду, см. `docs/DECISIONS.md`)
- LPR-интеграция — готово (backend `lpr-scoring` + web-admin `/lpr` +
  mobile; через стороннее платное API — Plate Recognizer, см.
  `docs/DECISIONS.md`). **Требует реального `LPR_API_KEY`** от
  пользователя в `.env` — без него модуль отвечает понятной ошибкой
  конфигурации вместо распознавания, это проверено.

## Этап 3 — Второй модуль и общая лента

- Второй модуль («прятки») — готово (backend + web-admin + mobile;
  верификация тем же секретным кодом при личном контакте, что и у
  авто-квеста, без GPS/фото-распознавания)
- Общий лидерборд клуба (сумма баллов по всем модулям сразу) — готово
  (`GET /modules/leaderboard/overall`, web-admin `/leaderboard`, mobile);
  сводная лента событий — готово (`GET /modules/feed/recent`, web-admin
  `/feed`, mobile `FeedScreen`) — последние `StatEvent` по всем модулям
  сразу, не по одному, с человекочитаемым `reason` и именем участника.
- Публикация статистики в чат (гл. 3.6) — готово полностью: точечные
  анонсы от авто-квеста и «прятки» при каждом начислении (как раньше,
  `config.announceRoomId` модуля) + новый агрегированный дайджест раз в
  час по всем модулям сразу (`DigestService`, `DIGEST_ROOM_ID` в `.env`,
  опционально — без переменной таймер не запускается). Точка отсчёта
  "последний дайджест" — в памяти процесса (теряется при перезапуске
  backend, тот же класс упрощения, что у presence в `CallsGateway`).
  Проверено вживую (реальный backend + Postgres + мок RC): дайджест по
  8 тестовым событиям из 2 модулей корректно агрегировал суммы и текст
  по каждому модулю, подтверждено по `__calls` мока.
- Push-уведомления — готово (`expo-notifications`, Expo Push API, без
  отдельного APNs/FCM ключа): начисление баллов (квесты/прятки/LPR) и
  результат модерации LPR присылают push на устройство. Push на новые
  личные сообщения — готово через исходящий вебхук Rocket.Chat
  (`ChatMessageWebhookController`, см. README для шагов настройки в
  админке RC); текст сообщения в push не попадает (защита секретного
  чата — превью на заблокированном экране не должно раскрывать
  содержимое). Только личные сообщения (`d`) — для групп/каналов резолв
  участников не сделан. ⚠️ Не проверено вживую против реального RC (нет
  Docker-демона, мок-сервер не реализует Integrations) — только
  unit-тесты + ручной POST с форматом payload по документации RC.
- Веб-чат участника (ТЗ 5.2) — готово (`web-admin/app/chat`, тот же
  REST-клиент/сессия, что у мобильного чата). Новые сообщения — realtime
  через DDP-подписку `stream-room-messages` (`RocketChatRealtimeClient`,
  порт mobile-клиента на браузерный `WebSocket`), не polling — если WS
  не поднялся, деградирует до polling раз в 4с, не падает молча.
  Ограничение: только текст (без отправки защищённых фото/видео из
  веба). Для прод-инстанса Rocket.Chat требуется явно включить CORS под
  origin веб-админки — см. `docs/DECISIONS.md`. Проверено вживую
  (Playwright, два независимых браузерных контекста + мок RC с
  реальным DDP-over-WebSocket): сообщение из контекста A доходит до
  контекста B за ~20мс, не за секунды.
- Перенос вёрстки Secret Chat UI Kit (web-admin `/chat` + mobile) —
  готово: трёхколоночная десктоп-раскладка (список/диалог/панель
  информации) в web-admin, аватары-силуэты и структура сообщений в
  mobile — см. `docs/DECISIONS.md`. Честные формулировки вместо кита:
  «Шифрование» описано как AES-256 at rest + HTTPS/WSS, без ложного
  заявления о сквозном (E2E) шифровании (по CLAUDE.md, правило 2).
- Звонки (аудио/видео) — готово: WebRTC 1:1-звонки поверх собственного
  сигнального WS-шлюза (`backend/src/calls`, `@nestjs/platform-ws`, не
  socket.io — см. `docs/DECISIONS.md`), клиенты в web-admin и mobile
  (`react-native-webrtc`), STUN/TURN через self-hosted `coturn` в
  `infra/docker-compose.yml` (публичный Google STUN — рабочий дефолт и
  без coturn). Верификация: 8 unit-тестов шлюза + сквозной звонок между
  двумя реальными браузерными клиентами (Playwright, два независимых
  контекста, `getUserMedia`/`RTCPeerConnection` с fake-media, живая
  передача медиа подтверждена) — mobile-клиент проверен только
  `tsc`/Jest, без живого устройства (в этой песочнице недоступно);
  `coturn` в docker-compose не проверен вживую (недоступен демон
  Docker), только по синтаксису и документации флагов.
- История звонков — готово: модель `Call` (Prisma), `CallsGateway`
  отслеживает активные звонки в памяти и пишет строку истории при
  `end-call`/`reject-call`/недозвоне (COMPLETED/REJECTED/MISSED/FAILED
  с реальными `startedAt`/`endedAt`), `GET /calls/history` (web-admin
  `/calls`, mobile `CallHistoryScreen`, оба доступны из профиля/меню).
  Проверено вживую: 5 новых unit-тестов сценариев + реальный звонок
  между двумя ws-клиентами (`call-user → accept-call → end-call`,
  пауза 1.2с) — одна и та же запись видна в истории обеих сторон,
  статус COMPLETED, длительность совпадает с реальной паузой.
  Вне объёма MVP: push при входящем звонке при закрытом приложении,
  запись разговора.
- Масштабирование сигнализации звонков на несколько backend-инстансов —
  готово: `CallsPresenceService` (Valkey — BSD-3-Clause, не Redis 8+,
  который tri-license RSAL/SSPL/AGPL, см. `docs/LICENSING.md`) —
  presence-набор `calls:online` + pub/sub-канал `calls:relay`. Локальная
  доставка остаётся быстрым путём (без похода в Valkey), общий канал
  используется только когда получателя нет на этом инстансе. Опционально
  — без `VALKEY_URL` работает как раньше, один backend-процесс.
  `infra/docker-compose.yml`: сервис `valkey`. Проверено: 16 unit-тестов
  `CallsGateway` (13 старых без изменения поведения + 3 новых на
  multi-instance-путь) + ручной прогон против реального `redis-server`
  (протокол идентичен Valkey) — два независимых объектных графа
  gateway+presence (эмулируют два backend-процесса, каждый со своей
  локальной `Map`) реально релеят сигнал друг другу через настоящий
  Redis-протокол-сервер по TCP, не через моки. Не хватает только
  прогона через реальный многоинстансовый `docker compose up
  --scale backend=2` — недоступно (нет Docker-демона в песочнице).
- Групповые звонки — готово: упрощённый mesh-вариант (без SFU/
  медиасервера), до 4 участников — новые события `join-call-room`/
  `leave-call-room`/`room-peers`/`peer-joined`/`peer-left`/
  `call-room-full` в `CallsGateway`, существующие `offer`/`answer`/
  `ice-candidate` переиспользованы без изменений (см.
  `docs/DECISIONS.md`, «Групповые звонки — mesh, до 4 участников»).
  Комнатой звонка служит сам `roomId` группового/канального чата —
  кнопки группового звонка в шапке чата видны только для не-DM комнат,
  для личных сообщений по-прежнему 1:1-флоу. Клиенты (web-admin и
  mobile) — сетка видео-плиток вместо единственного удалённого видео.
  Вне объёма: история групповых звонков (модель `Call` пишет только
  1:1), более 4 участников/SFU. Проверено вживую: 22 unit-теста
  `CallsGateway` (16 старых без изменения поведения + 6 новых на
  групповой протокол) + реальный сквозной прогон Playwright с 3
  независимыми браузерными контекстами — все трое видят видео друг
  друга (3 плитки на каждого), после выхода одного участника у
  оставшихся сетка корректно сжимается до 2 плиток.
- Автотесты — backend: готово (Jest unit — auth/users.ban/modules-registry
  начисление баллов; e2e — полный AppModule против отдельной тестовой БД
  на ключевые auth-эндпоинты). web-admin/mobile: готово точечно — не
  100% покрытие, а критичная бизнес-логика (API-клиенты, media/TTL-
  маркеры чата); рендер React/RN-компонентов не покрыт — потребовал бы
  отдельного jsdom/RTL стека, за рамками этого прохода.
- CI/CD — готово: `.github/workflows/ci.yml`, три параллельные джобы
  (backend/web-admin/mobile) на push в `main` и на каждый PR. Backend
  джоба поднимает Postgres как service-контейнер, гоняет unit- и
  e2e-тесты. Lint-шаг сознательно не включён — ни в backend, ни в
  web-admin нет рабочего eslint-конфига (пакет ещё не установлен/не
  настроен), включать здесь заведомо красный шаг не стали — это
  отдельная задача. Mobile-джоба ограничена `tsc --noEmit` + unit-
  тестами — нативная сборка (EAS/Xcode/Android SDK) требует реальных
  credentials разработчика и выполняется отдельно через `eas build`.

## Этап 4 — Продакшен-готовность

- Расширенная модерация чатов/медиа — готово: временный мут по комнате
  (прокси к нативному `channels.muteUser`/`groups.muteUser` Rocket.Chat,
  недоступен для личных сообщений — у RC для DM такого понятия нет),
  разбан (`POST /users/:id/unban`, зеркало `ban`), жалобы на сообщения
  (`MessageReport` — подать может любой участник, обработать/отклонить
  — модератор), удаление конкретного медиафайла из журнала доступа.
  Проверено вживую (curl, реальный backend+Postgres+мок RC): mute/unmute
  на группе, отказ мута на личке, полный цикл жалобы open→resolved,
  ban→unban, удаление медиа с последующим 404 по токену.
- Журналы аудита действий администраторов — готово: `web-admin/app/audit-log`
  теперь с фильтрами (действие, ID актора, тип объекта, диапазон дат) —
  `GET /audit-log` принимает `actorUserId`/`action`/`targetType`/`from`/`to`,
  проверено вживую (curl) на реальных записях (`user.ban`/`user.unban`/
  `chat.report.resolve`), пустой диапазон дат в будущем корректно даёт `[]`.
- Доп. защита медиа (водяные знаки, self-destruct-сообщения)
- Нагрузочное тестирование под пиковую активность мероприятий (гл. 4)
- Финальная проверка юридической готовности к сбору реальных ПДн
