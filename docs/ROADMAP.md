## Этап 1 — MVP (можно начинать сейчас, частично)

Цель: аутентификация по приглашениям + базовый чат (текст/фото/видео) +
защита медиа + профиль + минимальная админ-панель.

### Можно начинать без ожидания решений по DECISIONS.md:

1. **Схема БД** — пользователи, роли (расширяемая таблица ролей, не
   хардкод — см. ТЗ гл. 2), приглашения/инвайт-коды, объекты клуба
   (профиль/авто)
2. **Backend-скелет** — REST/GraphQL API для auth, приглашений, профилей;
   структура под будущий модульный реестр (гл. 3.5), даже если модулей
   ещё нет
3. **Система приглашений** — одноразовые/многоразовые/персональные
   инвайт-коды, заявки на вступление с модерацией (гл. 2.1)
4. **Аутентификация** — телефон/email, refresh-токены, 2FA обязательна
   для админ-ролей (принудительно на уровне привилегированных действий,
   не на уровне логина) — готово
5. **Admin-панель (базовый каркас)** — список участников, управление
   приглашениями, управление ролями

### Разблокировано решениями в DECISIONS.md, в разработке:

6. **Чат-ядро** — решено (Rocket.Chat, официальный образ, без лицензии
   Enterprise — см. `DECISIONS.md`). Реал-тайм текст/группы/каналы
   (мобильный REST/DDP-клиент, `chat-bridge` в backend) — готово. Фото/
   видео + защита медиа (см. п.7) — готово (фото; видео — без
   водяного знака, см. п.7). Модерация в web-admin (список
   комнат/сообщений, удаление сообщений, бан с деактивацией в RC,
   журнал доступа к медиа с фильтром по `SCREENSHOT_DETECTED`) —
   готово.
7. **Защита медиа (гл. 3.3)** — в разработке: собственное хранилище
   медиа через backend, шифрование at rest, токенизированная выдача,
   водяной знак на фото (`sharp`), журнал доступа,
   `react-native-capture-protection` на мобильном клиенте. Водяной знак
   на видео — открытый вопрос (ffmpeg-лицензия, см. `DECISIONS.md`).
   S3-совместимый `StorageAdapter` (`@aws-sdk/client-s3`, любой
   S3-провайдер через `endpoint`) готов — включается
   `MEDIA_STORAGE_DRIVER=s3` в `.env`, по умолчанию всё ещё локальная ФС.
8. **Деплой/инфраструктура** — зависит от хостинга (решено: облако, но
   конкретный провайдер не выбран) — локальная разработка через
   `infra/docker-compose.yml` не блокируется.

## Этап 2 — Модули и LPR

- Модульная система: реестр модулей, единый интерфейс интеграции (гл. 3.5) — готово
- Система баллов/статистики (референс — архитектура Oasis, своя реализация) —
  журнал событий + лидерборд по модулю готовы, web-admin `/modules` готов
- Первый игровой модуль (авто-квест) — готово (backend + web-admin +
  mobile; без LPR/геолокации — верификация чекпоинта по секретному
  коду, см. `docs/DECISIONS.md`)
- LPR-интеграция — готово (backend `lpr-scoring` + web-admin `/lpr` +
  mobile; через стороннее платное API — Plate Recognizer, см.
  `docs/DECISIONS.md`). **Требует реального `LPR_API_KEY`** от
  пользователя в `.env` — без него модуль отвечает понятной ошибкой
  конфигурации вместо распознавания, это проверено.

## Этап 3 — Второй модуль и общая лента

- Второй модуль («прятки») — готово (backend + web-admin + mobile;
  верификация тем же секретным кодом при личном контакте, что и у
  авто-квеста, без GPS/фото-распознавания)
- Общий лидерборд клуба (сумма баллов по всем модулям сразу) — готово
  (`GET /modules/leaderboard/overall`, web-admin `/leaderboard`, mobile);
  сводная лента/дайджест событий (не только сумма баллов) — не начато
- Публикация статистики в чат (гл. 3.6) — частично: авто-квест и
  «прятки» публикуют анонс каждого начисления баллов best-effort в
  указанную комнату (`config.announceRoomId` модуля); сводной ленты/
  дайджеста по всем модулям сразу нет
- Push-уведомления — готово (`expo-notifications`, Expo Push API, без
  отдельного APNs/FCM ключа): начисление баллов (квесты/прятки/LPR) и
  результат модерации LPR присылают push на устройство. Новые сообщения
  в чате push не шлют — они идут напрямую через Rocket.Chat realtime,
  минуя backend; для push на них потребовался бы отдельный исходящий
  webhook от Rocket.Chat, не реализовано.
- Веб-чат участника (ТЗ 5.2) — готово (`web-admin/app/chat`, тот же
  REST-клиент/сессия, что у мобильного чата). Ограничения: обновление
  сообщений поллингом раз в 4с (не realtime через DDP), только текст
  (без отправки защищённых фото/видео из веба). Для прод-инстанса
  Rocket.Chat требуется явно включить CORS под origin веб-админки —
  см. `docs/DECISIONS.md`.
- Автотесты — backend: готово (Jest unit — auth/users.ban/modules-registry
  начисление баллов; e2e — полный AppModule против отдельной тестовой БД
  на ключевые auth-эндпоинты). web-admin/mobile: готово точечно — не
  100% покрытие, а критичная бизнес-логика (API-клиенты, media/TTL-
  маркеры чата); рендер React/RN-компонентов не покрыт — потребовал бы
  отдельного jsdom/RTL стека, за рамками этого прохода.
- CI/CD — готово: `.github/workflows/ci.yml`, три параллельные джобы
  (backend/web-admin/mobile) на push в `main` и на каждый PR. Backend
  джоба поднимает Postgres как service-контейнер, гоняет unit- и
  e2e-тесты. Lint-шаг сознательно не включён — ни в backend, ни в
  web-admin нет рабочего eslint-конфига (пакет ещё не установлен/не
  настроен), включать здесь заведомо красный шаг не стали — это
  отдельная задача. Mobile-джоба ограничена `tsc --noEmit` + unit-
  тестами — нативная сборка (EAS/Xcode/Android SDK) требует реальных
  credentials разработчика и выполняется отдельно через `eas build`.
